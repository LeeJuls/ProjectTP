# 🤝 에이전트 팀 설계

> UE 5.8 HD-2D 턴제 PvP 배틀을 만드는 **멀티에이전트 팀 청사진**.
> **PM**(메인 대화)이 오너와 대화하고 팀을 발주·조율한다. **가장 어려운 판단**(plan 기본 설계·막힌 문제 진단)은 서브에이전트 **director**(Fable)에게 위임한다.
> 정답 소스는 `CLAUDE.md`(프로젝트 루트) — 이 문서는 그 청사진을 풀어 쓴 것. 어긋나면 `CLAUDE.md`가 맞다.
> 관련: [[projectTP_허브]] · [[작업로그_HD2D아트검증_플레이북]] · [[언리얼_MCP_실전노하우]]

## 📌 구조 원칙 (2026-08-12 개정)

~~메인 대화 = Director. Subagent는 서로 못 부른다. 오직 Director만 팀을 지휘한다.~~

→ **메인 대화 = PM**(Opus). 오너와 대화하고 일을 발주·수집하고 문서·커밋을 관리하며, **명백한** 게이트 판정을 내린다. Subagent는 서로 못 부르는 구조는 유지 — 다만 팀의 정점이 PM 하나에서 **PM + director 둘**로 나뉘었다.

**정정 사유(2026-08-12, 오너 지적)**: *"가장 중요한 설계에 fable을 하나도 안 쓰고 있다."* 개정 전 구조는 "Fable/Opus = Director(메인 대화) 자신"으로 정의해뒀지만, 실제로는 메인 대화가 계획·판단·발주·문서·커밋을 전부 겸했고 **Fable은 규칙에만 있고 한 번도 호출되지 않았다.** 이번 재편은 "가장 어려운 판단"을 **별도의 서브에이전트(director)로 분리**해 호출을 구조적으로 강제한다.

- **Fable 토큰 효율**: "머리"(계획 골격·막힌 문제 진단)만 Fable(director), 그 앞뒤를 감싸는 조율은 Opus(PM), "손"(반복 실행)은 Sonnet.
- **모든 에이전트는 [[projectTP_허브]] 상단 CLAUDE.md 규칙 상속**: 근본원인 없는 수정 금지 / "됐습니다" 전 실증 / 커밋 접두사 `[C] type:` / push는 오너 확인.

## 🧭 PM ↔ director 분업

| | **PM**(메인 대화) | **director**(서브에이전트) |
|---|---|---|
| 모델 | Opus | **Fable** — 이 팀의 최상위 |
| 하는 일 | 오너 대화 · 발주 · 수집 · 문서 · 커밋 · **명백한** 게이트 판정 | **plan 기본 설계** · **막힌 문제 진단** · 에이전트 보고 충돌 판정 |
| MCP | 있음 | **없음**(의도적) |

**director를 부르는 때 — 이 둘뿐**:
1. **새 기능·단계의 plan 착수** — 골격·게이트·유효범위·위험을 잡는다.
2. **막혔을 때** — 에이전트 보고가 충돌 / 결론이 의심스럽다 / 진단 3회 실패.

일상 진행·명백한 판정·문서 갱신에는 부르지 않는다. **비싼 모델을 노동에 쓰지 않는다.**

- **director는 MCP가 없다(의도적).** 호출 시점엔 대개 다른 에이전트가 에디터를 점유 중이고, 동시 접근은 브릿지를 마비시킨다([[언리얼_MCP_실전노하우]] 함정㉓). 진단 재료는 로그·git·wiki로 확보한다. 라이브 상태 조회가 꼭 필요하면 director가 "무엇을 조회해야 하는지"를 PM에게 요청한다.
- ★**맥락은 director가 스스로 확보한다.** 서브에이전트라 대화 맥락을 물려받지 못하므로, PM은 긴 브리핑 대신 **읽을 문서의 좌표**(plan·기능허브·raw 판정기록·노하우)를 준다. director.md 자체가 "판단 전에 문서를 직접 읽어라"를 최우선 지시로 명시한다.

## 🔍 두 검증자의 구분 (중요)

| | **qa-critic** | **verifier** |
|---|---|---|
| 질문 | "논리적으로 모순 없는가?" | "실제로 돌아가는가?" |
| 방식 | 설계·코드 적대적 리뷰 (사고 기반) | 빌드·실행·스크린샷 (실증 기반) |
| 시점 | 설계 단계부터, 교차검증 | 구현 후 |
| 대상 | 기획 모순·예외처리 누락·명세불일치 | 컴파일에러·크래시·렌더 실패 |
| 도구 | Read/Write/Glob/Grep/Bash/ToolSearch — **MCP 없음** | 위 + unreal-mcp 3종 + UmgMcp |
| 모델 | Opus | **Sonnet** |

**qa-critic 기본 태도 = 적대적(의심).** "이게 어떻게 깨지는가"를 찾는다. 발견 항목은 심각도순 리포트 → PM(필요시 director)이 수정 지시.

### ~~qa-critic은 MCP 조회 권한을 가진다~~ → 2026-08-12 회수

**사유**: qa-critic의 일은 **논리 검토**(사고 기반)이지 라이브 애셋 조회가 아니다. 그런데 MCP 접근권을 쥐고 있었다. 에디터는 **1개뿐**이라 다른 에이전트(구현자)와 동시 접근하면 브릿지가 마비된다([[언리얼_MCP_실전노하우]] 함정㉓). 리뷰는 문서·코드 Read만으로 충분하므로 회수했다.

### ★verifier: Haiku → Sonnet(2026-08-12 상향) + 게이트 강제

**계기(2026-08-11, E-S2)**: verifier 없이 gameplay-engineer가 **자기 구현을 자기가 검증**했고, *"이 환경에선 타이밍 검증이 구조적으로 불가능하다"*는 **틀린 결론**에 도달했다([[features/스킬연출구조/raw/E-S2_틱스로틀_진단]]). 실제로는 틱이 멎은 게 아니라 `bThrottleCPUWhenNotForeground`(기본값 `true`)로 PIE가 초당 3틱으로 스로틀된 것뿐이었다 — 원인은 엔진 로그 `up for play (max tick rate 3)` 한 줄, 그리고 [[언리얼_MCP_실전노하우]]에 3주 전부터 적혀 있던 함정⑦·§19였다.

**교훈 2건**:
1. **구현자는 자기 산출물 밖을 보지 않는다.** "검증됐다"는 말은 구현자 본인이 아니라 별도 에이전트가 확인해야 신뢰할 수 있다 → **verifier를 건너뛰지 않는다. 구현자 자가검증 금지.**
2. **검증은 시킨 것을 확인하는 일이 아니라 무엇을 볼지 고르는 일**이다(로그 프레임 카운터를 볼지, `max tick rate`를 볼지 같은 판단). Haiku엔 버거워 **Sonnet으로 상향**했다.

## 🔄 표준 워크플로우 (설계 → 구현 → 검증)

```
① 청사진 + plan 골격  ★director
      │
② 세부 plan            + designer(system-ui / balance)
      │
③ plan 피드백 + TC 제작  관련 에이전트 전원 + qa-critic (병렬)
      │
④ 단계별 반복: [개발 → ★verifier 실증 → PM 게이트 판정(막히면 director)] → 통과 시 다음 단계
      │
⑤ 풀 테스트             designer + qa-critic + verifier
```

- **TC 설계 = qa-critic, TC 실행 = verifier, 게이트 판정 = PM**(막히면 director로 이관).
- **2단 검증**: qa-critic(논리) → verifier(실증)은 다른 검증이다.
- ★★**verifier를 건너뛰지 마라 — 구현자 자가검증 금지.** 근거는 위 §verifier 상향 사유.
- 이월(deferred): 이후 단계서 검증되는 TC는 PM 확인 후 넘긴다.
- 독립적인 일은 한 메시지에서 **여러 에이전트 병렬** 호출 — 단, 아래 "독립의 기준" 참조.
- HD-2D "멋짐"의 최종 미적 판단과 push는 **오너(인간)**. art-director는 스크린샷으로 제안만.

## ⚠ "독립"의 기준 — 같은 UE 에디터를 안 쓴다 (2026-08-12 추가)

병렬 발주 시 "서로 다른 파일을 건드리니 독립"만으로는 부족하다. **MCP는 언리얼 에디터 1개를 공유**하므로, 두 에이전트가 동시에 MCP를 쓰면 그것만으로 브릿지가 마비된다([[언리얼_MCP_실전노하우]] 함정㉓).

→ **"독립"의 기준에 "같은 UE 에디터를 안 쓴다"를 포함**한다. 한쪽이 MCP로 에디터를 점유 중이면, 병렬로 붙이는 다른 쪽 지시서에는 **"MCP 금지"를 명시**해야 한다(이 세션에서 실제로 그렇게 발주했다 — 문서 편집 전담 에이전트에게 `mcp__unreal-mcp__*` 사용 금지를 못박음).

★**미결 과제**: 이 안전장치는 현재 **PM이 매번 손으로 지시서에 써넣는 방식**이라 빠뜨릴 위험이 있다. 구조적으로 강제하는 방법(예: 지시서 템플릿에 체크리스트 고정, 에이전트 정의에서 병렬 여부를 명시)은 아직 없다 — 다음에 이 문서를 만지는 사람이 풀어야 할 미결 과제로 남긴다.

## 💰 모델 배분 전략 (Fable = 두뇌, 양 끝단만)

작업 100 = **10 계획·방향 → 80 실행 → 10 방향부합 검수**. **Fable은 맨 앞·맨 뒤만.**

| 모델 | 누구 | 왜 |
|---|---|---|
| **Fable** | ★director | plan 골격 · 막힌 문제 진단 — 이 팀에서 가장 어려운 판단 |
| **Opus** | PM(메인) · qa-critic · system-ui-designer · balance-designer | 오너 대화·조율 / 적대적 검출 / 설계 |
| **Sonnet** | gameplay-engineer · scene-builder · art-pipeline · umg-engineer · hd2d-art-director · cpp-engineer · ★verifier | 구현·실행 전부 |

- **철칙**: Fable은 노동하지 않는다. 방향을 정하고, 결과가 그 방향에 맞는지 판단할 뿐. 중간 실행에 Fable 쓰면 낭비.
- ★**그런데 반대 실패가 실제로 있었다**(2026-08-11 오너 지적): *"가장 중요한 설계에 Fable을 하나도 안 쓰고 있다."* 규칙을 써놓고 **한 번도 호출하지 않은** 채 메인 대화가 전부 겸했다. **아끼는 것과 안 쓰는 것은 다르다** — 계획 착수와 막힌 문제에는 **반드시** 부른다. 이번 PM/director 분리는 이 실패를 구조로 막기 위한 조치다.
- **저비용 룰**: 문서 탐색·조회, 검증된 결과물의 반복 적용, 커밋·푸시 등 기계적 작업은 **sonnet/haiku**로(서브에이전트 위임 포함). Fable/Opus 금지.
- **frontmatter model은 기본값** — 필요시 Agent 호출 시 `model`로 오버라이드 가능(예: hd2d-art-director는 기본 Sonnet이지만 룩 "설계" 단계에선 상위 모델로 오버라이드하는 선택지가 있다).
- 작업 중간 산출물도 **전부 Obsidian wiki에 기록**: [[문서화_규칙]] 준수.
