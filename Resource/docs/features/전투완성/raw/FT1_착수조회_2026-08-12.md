# FT1 착수조회 — `ReceiveBeginPlay` 종단 + `NotifySkillSelected`/`NotifyUnitClicked` 파라미터 핀 (2026-08-12)

> 선행: [[BT3_MA_상세설계서]] §4-1·§4-2·§4-4·§10(#9·#10) · [[../../스킬연출구조/raw/AT4-b-2_결과_2026-08-12|AT4-b-2_결과]] · [[전진로직_실체_확정]] · [[../../../reference/언리얼_MCP_실전노하우|언리얼_MCP_실전노하우]] 함정107
> 규율: `BP_BattleManager` **조회만**(`find_nodes`/`get_node_infos`/`get_connected_subgraph`/`list_graphs`/`list_functions`/`list_events`). `connect_pins`·`create_node`·`set_pin_value`·`compile_blueprint`·`save_assets` **전부 미호출**. PIE 미실행.

## 결론 5줄

1. ★★**조회1 — `ReceiveBeginPlay` 종단 미배선 확정, 단 "종단"의 정체가 예상과 다르다.** `BP_BattleManager`의 BeginPlay 이벤트(`K2Node_Event_0`, EventGraph)는 **`then` 출력 핀이 애초부터 완전히 비어 있다** — 이 노드 뒤에 어떤 기존 초기화 체인도 없다. `get_connected_subgraph`로 재확인해도 도달 가능한 노드가 이 이벤트 노드 1개뿐이다. **FT1-1b/1c 착수 차단이 해소됐다** — 덮어쓸 기존 로직이 없다.
2. ★단 **FT1-1b와 FT1-1c가 나중에 둘 다 이 자리에 붙을 것이므로**, 지금은 비어 있어도 §4-2가 경고한 함정107(`connect_pins`가 출력 exec 핀을 덮어쓴다)이 **두 스캐폴드 사이에서 그대로 재현될 것**이다 — 먼저 붙는 쪽은 안전하지만 나중에 붙는 쪽이 `connect_pins`로 같은 `then`에 다시 이으면 먼저 것을 무음으로 끊는다. **선제적으로 `Sequence` 노드를 먼저 심고 `Then_0`(1b)/`Then_1`(1c)로 나눌 것을 권고**한다(§4-2 원안과 동일 결론, 단 사유는 "기존 체인 보호"가 아니라 "신규 스캐폴드끼리의 충돌 방지"로 정정).
3. ★★**조회2 — `NotifySkillSelected`/`NotifyUnitClicked` 둘 다 파라미터 1개씩 확정, [[BT3_MA_상세설계서]] §2의 "무인자" 서술 오류가 완전히 해소됨.** `NotifySkillSelected(SkillId: Integer)`, `NotifyUnitClicked(ClickedUnit: BP_BattleSpawnPoint 오브젝트 레퍼런스)`. §4-1(SkillId 인자 사용)이 맞았고, §2가 인용 범위를 초과했던 것(`NotifyAttackButtonClicked` 실측을 일반화)이 실측으로 확정 정정됐다.
4. ★**`NotifyUnitClicked`의 타겟 인자는 액터 레퍼런스다(인덱스 아님)** — §6-2 설계(`ResolveSlotToActor`류로 슬롯→액터 해석 후 액터를 그대로 전달)가 핀 타입과 정확히 일치한다. FT1-1a는 반드시 액터 참조를 만들어 넘겨야 한다.
5. **편승(저비용) — [[BT3_MA_상세설계서]] §10 #7 부분 해소**: `BP_BattleManager`의 함수 25개 전수 나열에 `ResolveSlotToActor`류 이름은 **없다**(신규 작성 필요, 단 `BP_BattleSpawnPoint` 등 다른 BP는 이번 세션에서 미조회이므로 "완전 부재"가 아니라 "이 BP엔 없음"으로만 확정). `max tick rate`: PIE 미실행이라 해당 없음. 규율: `is_dirty=false`(사후 확인), `git -C Content status --porcelain` 공백 확인.

## 조회 1 — `ReceiveBeginPlay` 종단 exec 핀

### 그래프 탐색

`list_graphs(BP_BattleManager)` 27개 그래프 전수 확인 — `ReceiveBeginPlay` 전용 함수 그래프는 **없다**(별도 오버라이드 함수가 아니라 EventGraph 안의 이벤트 노드로 구현). `list_events(BP_BattleManager)`에서 `ReceiveBeginPlay`가 `bIsImplemented: true`로 확인됨.

`find_nodes(EventGraph, title="BeginPlay", entry_points_only=True)` → 정확히 1개:
```
/Game/Blueprints/BP_BattleManager.BP_BattleManager:EventGraph.K2Node_Event_0
```
(`title="ReceiveBeginPlay"`/`"Event BeginPlay"`로도 검색했으나 0건 — 노드 타이틀은 `"BeginPlay"`로만 매칭됨)

### 핀 원문 (`get_node_infos`)

```
node: K2Node_Event_0
type_id: "이벤트추가|BeginPlay이벤트"
input_pins: []
output_pins:
  [0] name=OutputDelegate, type_id=델리게이트, connected_pins: []
  [1] name=then,           type_id=실행,       connected_pins: []   ← ★종단, 미배선
```

### 하류 무접촉 재확인 (`get_connected_subgraph`)

`get_connected_subgraph(K2Node_Event_0)` → 반환 노드 **1개**(`K2Node_Event_0` 자기 자신뿐). 이 이벤트에서 도달 가능한 다른 노드가 **0개**라는 뜻 — `then` 핀의 `connected_pins: []`과 정합.

### 판정 — ★FT1-1b/1c 착수 차단 해소, 신규 제약 1건 추가

- **차단 해소**: 종단(`K2Node_Event_0.then`)이 **미배선**이다. `connect_pins`로 여기 직접 이어도 끊길 기존 체인이 없다 — §4-2가 우려한 "기존 초기화 로직 무음 절단" 시나리오는 **이 BP에는 해당하지 않는다**(BeginPlay 자체가 원래부터 비어 있었다).
- **신규 제약**: 그럼에도 **FT1-1b와 FT1-1c가 같은 핀을 순차로 채울 것**이므로, 두 번째로 붙는 스캐폴드가 `connect_pins`를 그대로 쓰면 첫 번째를 무음으로 끊는다(함정107은 "기존 체인이 있었는가"와 무관하게 "이미 배선된 출력 핀에 또 이으면"이 조건이다 — 1b가 먼저 붙으면 그 순간부터 `then`은 "배선됨" 상태가 되고, 1c가 그 뒤에 오면 위험이 재현된다). **권고**: FT1-1b 구현 시점에 처음부터 `Sequence` 노드를 심어 `Then_0`(1b 로직)/`Then_1`(1c 예약)로 분기해두면, FT1-1c는 나중에 `Then_1`에 additive로 붙이기만 하면 된다.
- BeginPlay가 원래부터 비어 있다는 사실 자체도 기록 가치가 있다 — `BP_BattleSpawnPoint`(유닛 액터)는 `BeginPlay`에서 `DT_JobStats` 조회 등을 한다는 게 기존 문서([[전투BP_현황도_2026-08-11]])에 있었지만, **매니저 액터 자신의 BeginPlay는 로직이 없다**(초기화는 `RegisterUnitReady`→`InitBattle` 경로로 위임된 구조로 추정 — 이번 조회 범위 밖, 단정하지 않음).

## 조회 2 — `NotifySkillSelected` / `NotifyUnitClicked` 파라미터 핀

두 함수 모두 `list_graphs`에서 전용 Function Graph로 확인됨(`.../BP_BattleManager:NotifySkillSelected`, `.../BP_BattleManager:NotifyUnitClicked`).

### 2-1. `NotifySkillSelected`

`FunctionEntry` 핀 원문:
```
node: NotifySkillSelected.K2Node_FunctionEntry_0
type_id: "|NotifySkillSelected"
input_pins: []
output_pins:
  [0] name=then,    type_id=실행,   connected_pins: [ IfThenElse_0.execute ]
  [1] name=SkillId, type_id=인티저(Integer), value="", connected_pins: [
        CallFunction_1(GetSkillCooldown).SkillId (index 3)
        VariableSet_0(SetPendingSkillId).PendingSkillId (index 1)
        CallFunction_3(ToString(Integer)).InInt (index 0)
      ]
```
★**execute+self 외 파라미터는 `SkillId`(Integer) 1개뿐**, 기본값 없음(리터럴 미설정 — 반드시 호출 시 값 주입 필요).

**1홉 목적지**:
- `GetSkillCooldown(Unit=ActiveUnit, SkillId=SkillId)` → `ReturnValue`(Integer) — 쿨다운 조회
- `SetPendingSkillId(PendingSkillId=SkillId)` — 변수 저장(§4-1이 언급한 `PendingSkillId` 갱신 지점 실측 확인)
- `ToString(Integer)(InInt=SkillId)` → `ReturnValue`(String) — DataTable RowName 변환 등에 쓰이는 것으로 추정(1홉 밖, 단정 안 함)

### 2-2. `NotifyUnitClicked`

`FunctionEntry` 핀 원문:
```
node: NotifyUnitClicked.K2Node_FunctionEntry_0
type_id: "|NotifyUnitClicked"
input_pins: []
output_pins:
  [0] name=then,        type_id=실행,  connected_pins: [ IfThenElse_0.execute ]
  [1] name=ClickedUnit, type_id="BP Battle Spawn Point 오브젝트 레퍼런스", value="", connected_pins: [
        VariableGet_3(GetbIsParty).self (index 0)
        CallFunction_5(GetDisplayName).Object (index 0)
        MakeArray_0.[0] (index 0)
        CallArrayFunction_0(ContainsItem).ItemToFind (index 1)
      ]
```
★★**타겟 인자 형식 = 액터 레퍼런스다.** `ClickedUnit`의 `type_id`가 정확히 `"BP Battle Spawn Point 오브젝트 레퍼런스"` — 인덱스/정수/문자열 슬롯ID가 아니라 **`BP_BattleSpawnPoint` 액터 오브젝트 레퍼런스**를 직접 받는다.

**1홉 목적지**:
- `GetbIsParty(self=ClickedUnit)` → `bIsParty`(bool) → `PromotableOperator_1`(비교 연산, 진영 판정으로 추정)
- `GetDisplayName(Object=ClickedUnit)` → `ReturnValue`(String) → `FormatText_1`(로그 문자열 조립으로 추정)
- `MakeArray([0]=ClickedUnit)` → `Array` → `VariableSet_2`(1홉 범위 밖이라 대상 변수명 미확인)
- `ContainsItem(TargetArray=<CallFunction_0 결과>, ItemToFind=ClickedUnit)` → `ReturnValue`(bool) → `IfThenElse_2` — ★[[전투BP_현황도_2026-08-11]] §상태표 6행이 서술한 *"`ResolveTargetPool` 결과 포함 여부(`ContainsItem`) 확인"* 가드가 핀 단위로 실측 확인됨.

### 판정 — ★FT1-1a 착수 차단 완전 해소

- [[BT3_MA_상세설계서]] §2의 정정 서술(*"`NotifySkillSelected`/`NotifyUnitClicked`는 미확인"*)이 이번 조회로 닫힌다. §4-1 배선 설계(`NotifySkillSelected(SkillId)` 호출)는 **핀과 정확히 일치** — 무인자로 배선했다면 §2가 경고한 대로 컴파일 자체가 실패했을 것(필수 파라미터 미연결)이므로, "PendingSkillId 잔값으로 매턴 발화" 위험 시나리오는 **BP 자체가 컴파일 에러로 막아준다**(단, 그렇다고 파라미터 값 자체가 항상 옳다는 보장은 아니다 — MA 훅이 잘못된 `SkillId`를 넣으면 컴파일은 되지만 여전히 오염 가능).
- §6-2(`ResolveSlotToActor`류 런타임 리졸버로 액터 해석 후 `NotifyUnitClicked`에 전달) 설계가 **핀 타입으로 확정 뒷받침**됨 — FT1-1a는 슬롯ID→액터 변환을 반드시 거쳐야 하며, 그 변환기가 아직 없다는 것이 아래 편승 조회에서 재확인됨.
