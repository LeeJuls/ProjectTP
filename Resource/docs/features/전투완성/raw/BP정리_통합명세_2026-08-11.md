## 0. 결론 (오너용 4줄)

1. **오너 지적이 맞다.** 데이터 이관 명세는 있는데 **BP에서 무엇이 빠지는지**를 한 곳에 모은 문서가 없었고, 그 결과 **하드코딩 실측 30건 중 14건이 어떤 단계에도 배정돼 있지 않다.**
2. **두 계획은 같은 파일을 건드린다.** `BP_BattleManager` EventGraph의 `EnterExecuting` 체인을 F7b ④⑤⑦과 스킬연출구조 C5·C14가 **둘 다** 편집한다. 실행 순서상 동시 편집은 없지만, **⑩a(비가역)가 그 사이에 끼어 있어 D6 구간은 롤백 경로가 없는 상태로 진행**된다.
3. **명세 충돌 1건 확정**: `IfThenElse_5`(피격 리액션 게이트)를 **C5와 C14가 이중 배정**하고 있으며 지시가 서로 반대다(C5="Condition 핀만 교체·exec 무변경" / C14="2분해·exec 분기 추가"). **C5에서 `IfThenElse_5` 절을 삭제**해야 한다.
4. **가장 위험한 미배정**: `ResolveHit` 인라인(쿨다운·BattleLog) **제거 단계가 F7b 어디에도 없다.** ⑦ 게이트(오라클-diff 전 행 0)가 통과하려면 ⑦ 커밋 안에서 죽어야 하는데, ⑦의 롤백 레시피에는 그 복원이 없다.

**숫자**: 미매핑 하드코딩 **14건** / 미배정 구현항목 **12건** / 계획 충돌 **3건** / 완료 판정 체크리스트 **32항목**.

## 4. 명확화 요구 5건 — 답

### 4-1. ⑦에서 `ResolveHit` 인라인(쿨다운·BattleLog)은 **언제 죽는가** → **명시된 단계가 없다 [Critical, CONFIRMED]**

**사실관계 3개**

| # | 문서 | 문구 |

| a | F7b v2 ⑤ | *"`ResolveHit`의 인라인 쿨다운·BattleLog 방출은 **⑦까지 유지 — 제거 금지**"* |
| b | F7b v2 ⑤ 게이트 | *"인라인 방출 무손실(**이중 방출 0** — dead라 자연 충족, **⑦ 후 재확인**)"* |
| c | F7b v2 ⑩a | *"`Effect*`/`PowerRate` **구컬럼** 제거"* — **DT 컬럼이지 BP 노드가 아니다** |

**논리적 귀결**: ④a가 `ApplyEffectEntry`의 `DAMAGE`를 `ResolveHit(Attacker,Target,DamageCoeff)`로 연결하므로 **⑦ 이후에도 `ResolveHit`은 살아 있고, 인터프리터를 통해 호출된다.** 그러면 인라인 쿨다운·BattleLog도 같이 발화한다.

- **캐스트당 DAMAGE 1엔트리**: `BattleLog` **2줄** (인터프리터 1 + 인라인 1) → ⑦ 게이트 *"오라클-diff 전 행 0"*이 **행수부터 FAIL**.
- **캐스트당 DAMAGE N엔트리**(멀티히트): 인라인이 **N회** 발화 → `BattleLog` N줄 + 쿨다운 N회 세팅 = [[F7_스킬아키텍처_확정]] §8-6이 경계한 **멀티히트 자충돌**. `skills_merged_42.csv` 실측에 **`HitCount=2` 2행 · `=3` 1행**이 이미 있으므로 가정이 아니다.

**⇒ 인라인은 ⑦ 커밋 안에서 죽어야 한다.** 그런데 ⑦의 롤백 스톱은 *"실패 시 `EnterExecuting→ResolveHit` 원복"* **한 줄뿐**이다. 인라인 노드를 삭제한 상태에서는 그 원복이 **기능을 복구하지 못한다**(쿨다운·로그가 없는 라이브가 된다).

|---|---|---|
| **⑦-1** | `EnterExecuting` 재배선 + 인라인 쿨다운·BattleLog **exec 연결만 절단**(노드·핀 보존, 고아화) | **핀 2개 원복**으로 완전 복구 |
| **⑦-2** | ⑦-1 게이트 GREEN 확인 후 고아 노드 **물리 삭제** | 세이브포인트 |

### 4-2. ⑩a가 **비가역·스톱**인 이유와 전후 롤백 경로 변화 [설명]

**이유**: ⑦까지의 유일한 롤백은 *"`EnterExecuting`을 `ResolveHit` 직결로 되돌린다"*이고, **그 경로가 동작하려면 `PowerRate`·`Effect*` 값이 DT에 남아 있어야 한다.** ⑩a가 그 컬럼을 지우는 순간, 핀을 되돌려도 인라인 판정이 읽을 데이터가 없다 → **원복이 기능 복구가 아니게 된다.** "구컬럼 병존 = 인라인 복구선 생존"이 그 뜻이다.

| 시점 | 롤백 수단 | 비용 |
|---|---|---|
| ⑩a **전** | 핀 원복 (+ DT 무접촉) | 수 분 · MCP로 가능 |
| ⑩a **후** | uasset 세이브포인트 복원 **+** DT 재임포트 **+** struct 역편집(**오너 수동 세션**) | 세션 단위 · MCP 브릿지 마비 동반 |

**⇒ D6 전 구간(순서 13~22)은 「롤백 없음」 상태에서 진행된다.** 따라서 D6는 **커밋을 잘게 쪼개고 커밋마다 세이브포인트**(SHA256 manifest + `find_nodes(title="")` 텍스트 스냅샷)를 남기는 것이 절차상 **선택이 아니라 요구**다.

### 4-3. **C1(struct)이 왜 ⑦이 아니라 ⑩a 이후인가** — 그리고 표현이 부정확하다 [Medium, CONFIRMED]

**⑦이 아닌 이유 2개**
1. **롤백선 보호**: C1의 제거 목록 #12~16이 곧 ⑩a 대상 구컬럼이다. ⑦ 시점에 지우면 §4-2의 복구선이 ⑦ 게이트 도중에 사라진다. ⑦은 *"최대 회귀 표면 · 단독 게이트"*라 롤백선이 살아 있어야 하는 유일한 단계다.
2. **세션 비용**: struct 편집 모달은 **MCP 브릿지 전체를 마비**시킨다(함정㉓). 비용은 편집 수가 아니라 **세션 수**에 비례하므로 추가 6 + 제거 10을 한 번에 묶어야 하고, 그게 가능한 최초 시점이 ⑩a다.

**★그러나 "⑩a **이후**"라는 표현은 부정확하다.** C1의 제거 5개는 **⑩a의 수술 내용 그 자체**다. 순서로 쓰면 `⑩a → C1`인데 `C1 ⊇ ⑩a(struct분)`이므로 **순환**으로 읽힌다.

> **정정 제안**: `⑩a`와 `C1`은 **동일 세션의 한 편집**이다. 정확한 표기는
> `⑩a(BP 舊리더 제거) → [C1 = ⑩a struct분(제거 5) ∪ 스킬연출구조분(추가 6 + 제거 5)] = D5.5 1세션 → C2·C3 동일 세션 → 임포트 → C4·C5·…`

### 4-4. C4·C14가 각각 **같은 커밋이어야 하는** 이유

### 5-1. [High, CONFIRMED] 턴 예산 모델 `EstimatedTurnSec`(R-9)이 **라이브 exec 구조와 다르다**

**라이브 턴 위상**(W2 실측):
```
HideAll → WalkForward(즉시반환, 내부 latent 0.4s) → Delay(0.55) → PlayAttack(내부 RetriggerableDelay로 ~0.58s 블록)
   → Sequence ├ then_0: Delay(0.25) → IsValid → TakeHit
              └ then_1: Delay(0.75) → WalkBack → Delay(0.45) → EnterTurnEnd
```
**R-9 모델**: `접근(ApproachSec) + 캐스트FX + 투사 + (HitCount−1)×HitIntervalSec + 임팩트FX + 복귀(ApproachSec) ≤ SlotBudgetSec`

두 식에 **공통항이 `ApproachSec` 하나뿐**이다. 실제 턴 길이를 지배하는 `0.55`·`0.25`·`0.75`·`0.45`(H06~H09)와 `PlayAttack` 내부 블록(H18)은 **모델에 없다**.

**귀결 3개**
1. **`HitIntervalSec` ≠ `Delay(0.25)`.** Director 질의에 답한다 — 의미가 다르다. `Delay(0.25)`는 *"모션 시작 → 임팩트 판정"* 오프셋이고, `HitIntervalSec`는 *"멀티히트 타격 간 간격"*이다. 값이 우연히 같을 수는 있어도 **같은 축이 아니며, 0.25가 커버된 것으로 보면 안 된다.** (D1 §13 N5는 `HitIntervalSec`의 실값 출처조차 지정하지 않았다 — `MaxHitCount`·`SlotBudgetSec`·`ProjectileFlightBudgetSec`만 열거.)
2. **L27(턴 예산 린트)이 런타임에 영향 없는 양을 구속**한다. 위 Delay들을 계산값으로 재배선하지 않는 한, `vfx.FPS`를 10→20으로 바꿔도(D5 판정3) 턴 길이는 안 변한다. **판정3의 정량 근거(3.25s→1.85s)는 모델 위의 값이지 실측 턴 길이가 아니다.**
3. **L27은 T3(임포트 직전) 게이트인데 "D6 실측 전 실행 불가"**로 표기돼 있다 → 임포트 게이트에 **실질 공백**이 생긴다.

**⇒ Director 판정 필요**: (a) H06~H09를 **명명 상수화까지만** 하고 L27을 *"설계 상한(비런타임)"*으로 격하 표기할 것인가, (b) Delay를 FX 지속 계산값으로 배선(= 리듬 상수의 **데이터 종속화**, plan 분류 ① 방침 변경)할 것인가. **어느 쪽이든 지금 정하지 않으면 D6가 (b)를 임의로 구현하고 MA-1이 깨진다.**
