## ★정정 1 — 프레임당 **0.117s가 아니라 0.125s**

director 판정문 §④와 PM 요약이 `0.70 ÷ 6 = 0.117`로 계산했다. **세이프마진을 이중 차감한 오류다.**

프로젝트 공용 공식이 이미 `vfx_draft.csv` Memo에 있다 — `표시시간 = FrameCount/FPS − 0.05`(H16). H17(코드의 캐릭터 FPS `8.0`)을 넣으면:

```
6 / 8.0 − 0.05 = 0.70   ← H18 ATTACK1 RetriggerableDelay, 정확히 일치
8 / 8.0 − 0.05 = 0.95   ← D2 핫픽스 전 값(FrameCount가 8이던 시절), 정확히 일치
```

**두 시점 모두 소수점까지 맞는다** → `0.70`은 *"6프레임 전체 길이"*가 아니라 **"전체 0.75에서 마진 0.05를 뺀 값"**이다.

→ **프레임당 = 1/8.0 = `0.125s`**, ATTACK1 전체 = **`0.75s`**.

### 정정된 유도표 — 근거가 **더 강해졌다**

| ID | 값 | 유도식 | 의미 | 정합 |

| **H08** | 0.75 | `6 / 8.0` | ATTACK1 전체 재생 | ✅ |
| **H18** | 0.70 | `6/8.0 − 0.05` | 표시 종료(마진) | ✅ |

| **H15** | 0.55 | `6/10 − 0.05` | legacy_hit | ✅ |

★**H17(캐릭터 FPS 8.0)이 8개 중 4개의 분모**다. director의 *"H17 C10 편입 권고"*는 **권고가 아니라 필수** — 상수화하지 않으면 (b′)의 분모가 없다.

**그래서 (a)인가 (b)인가**: 근거가 생겼다는 건 *"지금 배선하라"*가 아니라 ***"지금 무엇을 문서에 적을지 알게 됐다"***는 뜻이다. 박아두면 D6의 (b′)가 **노드 2개짜리 기계 작업**이 되고, 안 박아두면 **재설계**가 된다. 그리고 ★**H07이 오차 0으로 맞는다는 것 자체가 손대지 말 이유다** — 이미 맞아 있는 연출을 육안 없이 계산 노드로 바꿔 재현 실패하면 **기대 이득 0, 리스크 유한**.

## ★정정 2 — MA-1은 **타이밍을 고정하지 않는다**

`SPD원장_오라클_v1` §7 파싱 스키마(diff 기준의 유일 정의):
```
T, attacker, attacker_job, target, target_job, dmg, target_hp_after, died
```
★**시간 열이 없다.** §6 H2: *"판정은 전 행(공격자·대상·dmg·hpAfter·died) diff로만"*. §0에서 **난수 0·명중 100·회피 0·결정론** 확정 → **시간이 값에 개입할 경로가 구조적으로 없다.**

| 파급 | 내용 |
|---|---|
| director (a) 채택 근거 | *"(b)는 MA-1을 깬다"* → ❌ **성립 안 함.** 결론은 살지만 **근거를 교체**해야 한다. 안 그러면 누가 이 사실을 발견하는 순간 (a) 전체가 흔들린다 |
| ★director 판정문 PM확인 #3 | *"봉인 후면 **재봉인 필요**(잔상 절단이 원장을 바꾼다)"* → ❌ **바꾸지 않는다.** T1은 원장 8열 중 **0개**를 건드린다(표시 전용). 바뀌는 건 asset hash뿐 → ★**오너 세션 1회 절약** |

**MA 구현 조건 1개(B3에 명문화 요구)**: MA-1이 타이밍에 무감각한 것은 **훅이 상태 진입 구동**이기 때문이다. v2가 *"타이밍 필요 시 커스텀 이벤트 경유"*로 문을 열어뒀는데, **MA가 Delay 스케줄링을 쓰는 순간 MA-1은 턴 길이에 종속되고 그때는 (b′)가 실제로 MA-1을 깬다.**
→ *"MA 시나리오는 상태 진입 훅만으로 구동. 고정 Delay로 다음 명령을 스케줄하지 않는다."* + MA-2 검증항 추가: *"MA 그래프 내 Delay 노드 0개."*

## ★★발견 — H18 "PlayAttack 0.58s 블록"은 **측정 아티팩트일 가능성이 높다**

### 근거

W2 실측 4개 값이 **전부 1/3의 배수**다: `0.333` / `2.333` / `3.0`.

★결정적 단서: **TurnEnd(2.333) → 다음 TurnStart(3.0) = 0.667인데, 그 구간의 Delay는 `EnterTurnEnd`의 0.35 하나다.** `0.35 → 0.667`은 **틱 양자화(1/3s 격자)** 말고는 설명이 안 된다.

양자화가 있다면 앞 구간도 전부 양자화된다:
```
Delay(0.55) → 0.667
Delay(0.75) → 1.000
Delay(0.45) → 0.667
            합 = 2.334   ← 실측 2.333과 정확히 일치. PlayAttack 블록 없이
```

| 가설 | TurnEnd 2.333 | 다음 TurnStart 3.0 |
|---|---|---|
| A: 블록 0.58 실재 + 양자화 없음 | ✅ | ❌ (2.683 예상) |
| ★**B: 블록 ≈0 + 3fps 양자화** | ✅ (2.334) | ✅ (3.000) |

W2 자신이 *"역산, 직접 로그 미채집"*이라고 자인한 값이 0.58이다.

### ★★A1과의 교차 지지 (PM 판정)

balance는 **A1 결과를 모르는 상태**에서 *"1/3s 격자"*를 유도했다. 같은 시각 A1(verifier)은 **`max tick rate 3`을 실측**했다.

★**1/3s = 3fps.** 두 조사가 **독립적으로 같은 수에 도달했다.** 가설 B의 신뢰도가 크게 올라간다.

★그리고 더 무거운 함의: **W2 실측 자체가 3fps 환경에서 이뤄졌다면, 과거 타이밍 실측 전반이 양자화로 오염됐을 수 있다.**

### 밸런스 영향 — 크다

| | 현행 인식 | 가설 B가 참이면 |
|---|---|---|
| 유닛턴 1회 | 3.0s | **2.10s** |
| even-trade 20턴 한 판 | 60s | **42s** |
| `SlotBudgetSec` 기준선 | 3.0 | **2.1 (−30%)** |

D6에서 3슬롯 FX를 얹을 때 예산이 3.0이냐 2.1이냐는 **43% 차이**다.
→ ★**`SlotBudgetSec` 확정 금지**(플래그 F6).
