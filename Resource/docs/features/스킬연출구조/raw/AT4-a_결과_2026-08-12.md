## `AU-A4-14` — 정적 2콜 실측 (PIE 불요, 세션 첫 액션)

### ① `AsyncLoadAsset` exec 핀 원문

`BP_FxLabQuad:EventGraph.K2Node_LoadAsset_1`(`PlayVfxInternal` 내부):

```
output pin index0 "then"      : connected_pins = []           ← 미연결
output pin index1 "Completed" : connected_pins = [CastToTexture2D.execute]  ← 연결됨
output pin index2 "Object"    : connected_pins = [CastToTexture2D.Object]
```

★**결론: `Completed`에 정확히 연결돼 있다.** 가설 (d)("then에 물림")는 **거짓**. AT4-pre가 인용한 `FXLAB:DIAG:LoadAsset.then fired`(16:24:55 세션)는 **과거의 진단용 임시 배선의 흔적**이고, 현재 그래프는 이미 정상 상태로 되돌아가 있다 — E-S2_FxLabQuad_결과.md의 "남은 부채: DIAG 진단 노드는 `break_pins`로 비활성화만 했다"는 기록과 정확히 부합한다(연결이 끊긴 것이지, 배선 자체가 `then`으로 바뀐 게 아니었다).

### ② `PrintString`/`PlayVfxInternal` 리터럴 전수 덤프

Append 노드의 리터럴 입력(`A` 핀, 미연결 상태의 실제 기본값)을 노드 단위로 직접 조회:

| 토큰 | 소스(분기) | 리터럴 원문(파서 접두어와 대조) |
|---|---|---|
| `FXNOROW` | `GetDataTableRow.RowNotFound` | `"FXLAB:FXNOROW:"` |
| `FXSKIP` | `Branch(frameCount≤0∨fps≤0).True` | `"FXLAB:FXSKIP:"` |
| `TEXMISS` | `CastToTexture2D.CastFailed` | `"FXLAB:TEXMISS:"` |
| `FXSHOW` | `SetVisibility(true).then` | `"FXLAB:FXSHOW:"` |
| `FXHIDE` | `SetVisibility(false).then`(RetriggerableDelay 이후) | `"FXLAB:FXHIDE:"` |

`tokens.py` 순번15b/15c의 prefix(`FXLAB:FXNOROW`/`FXLAB:FXSKIP`/`FXLAB:TEXMISS`/`FXLAB:FXSHOW`/`FXLAB:FXHIDE`)와 **문자 단위로 일치**(콜론 포함, 각 리터럴이 프리픽스로 시작). ★가설 (c)("토큰 리터럴 상이")도 **거짓**.

### ③ 재해석 — 60fps 세션 FXLAB 0건의 진짜 원인

(c)·(d) 둘 다 배제되면 남는 설명은 하나뿐이다: **그 3개 60fps 세션(16:28·16:31·20:06)에서 `PlayVfx`가 애초에 한 번도 호출되지 않았다.** `PlayVfxInternal`은 `BeginPlay`가 자동으로 부르지 않고(`BeginPlay`는 MID 초기화만 함), 외부 트리거(`TestDriver_TEMP` 커스텀이벤트 또는 오너의 수동 조작)가 있어야 발화한다. AT4-pre의 "실패가 아니라 60fps에서 한 번도 안 걸었다"는 표현이 정확했다 — 코드 결함이 아니라 **그 세션에서 재생 트리거가 안 눌렸다**는 뜻이다.

★**미확인**: 그 3개 세션에서 실제로 무엇이 조작됐는지(오너 수동 클릭인지, 다른 시도였는지)는 로그만으로 확정 불가. 이번 산출물(`BP_FxLabDummy`)로 향후 재현 시도 시엔 직접 트리거(폴링 변수) 경로가 있으므로 이 문제는 재발하지 않는다.

## 틱레이트 — `max tick rate 3`, ★신규 미스터리 아니라 **함정(100) 확정사항의 3차 재확인**

★먼저 `언리얼_MCP_실전노하우.md` §39~41(함정95·96·97·98·100)을 재확인했다 — **이미 두 번 조사되고 확정된 사안**이었다:

> 함정(100) 확정: *"사람이 앞에 있으면 60, 에이전트가 돌리면 3. 에이전트는 이를 바꿀 수 없다"*. 실무 규칙 3: *"'3fps를 우회해 보겠다'는 시도를 반복하지 마라. 두 번 조사해 두 번 다 불가였다."*

지시서가 "★60fps를 얻을 수 있는지 시도해보고 보고해라"로 **명시 재시도를 요청**했으므로, 규칙3과 상충하지만 지시를 따라 **3차 시도**를 실행했다:

| 시도 | 조회 결과(적용 전) | 조치 | 조회 결과(적용 후) | PIE 재시작 후 tick rate |
|---|---|---|---|---|
| `bThrottleCPUWhenNotForeground` | **이미 false**(함정100이 §40에서 이미 "설정은 원래부터 false"로 정정한 그대로) | 변경 없음(이미 원하는 값) | false | **3** |
| `bAllowSlateThrottling`(신규 확인 — "UI 인터랙션 중 백그라운드 처리를 제한") | true(기본값) | `SetSectionProperties`로 false 설정 + `SaveSection` | false(재조회로 확정) | **3** |

두 설정 모두 재조회로 적용된 것을 확인했음에도 `LogWorld: ... up for play (max tick rate 3)`가 그대로 나왔다. → ★**결과가 함정(100)의 확정 내용과 정확히 일치한다.** 즉 "설정과 무관하게 에이전트가 PIE를 켜면 3" — 새로 발견한 원인이 아니라 **기존 결론이 3번째로 재현**된 것. `bAllowSlateThrottling`을 새로 시도했다는 점만 추가 정보이고, 이 역시 tick rate에 영향이 없었으므로 **"설정 축은 이걸로 사실상 소진됐다"**로 다음 사람에게 넘긴다. 과거 60fps 3세션(16:28·16:31·20:06)의 실제 주체가 오너인지 에이전트인지는 이번에도 **미확인**으로 남지만, 함정(100)의 "에이전트는 60을 못 얻는다" 확정과 결이 맞다 — 그 3세션도 오너가 켰을 가능성이 높다는 쪽에 무게가 실린다.

**영향**: `PlayFlinch`의 `RetriggerableDelay(0.08)` 정밀 타이밍 검증은 **이월**(3fps에서 1틱=0.33s로 0.08s보다 굵음). 단 **값·개수·순서·발화**(사이클이 완주해 `bVisible`이 최종 `true`로 돌아옴, 토큰이 정확히 1회씩 발화)는 이번 세션에서 이미 안전하게 확인됨.
