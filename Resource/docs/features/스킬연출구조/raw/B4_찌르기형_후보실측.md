## 1. ★질문 ① — "추가 파일 예외 규약" 구체안

### 1-1. 문제 재확인

[[E_스파이크_plan]] 설계제약2(E-H6): *"`Content/` SHA256 manifest diff"*로 라이브 무손상을 판정한다. 그런데 Holy VFX 임포트는 **신규 텍스처 파일을 추가**하므로 diff가 반드시 non-zero가 된다 — 규약을 문자 그대로 적용하면 **정상적인 신규 임포트조차 FAIL**로 판정된다.

### 1-2. 기존 선례 재확인 — SHA256 manifest는 이미 git으로 대체됨

[[E-S1_레벨구축_결과]] E-S1-02가 실제로 쓴 판정:

> *"Content 저장소 변경 집합이 **정확히 `{map_battle_fxlab.umap}` 1개**"*

**SHA256 별도 도구 없이 git 추적 diff로 판정**했고(*"내용 해시가 같아야 diff 0"*), 이번 실측으로 메커니즘을 재확인:

```
$ cd D:\unreal\projectTP\Content && git status --porcelain --untracked-files=all
 M Data/F_SkillsRow.uasset
```

→ `git status --porcelain`이 **정확히** SHA256 manifest diff와 동치(내용 해시 비교, mtime 무관 — S1이 이미 실증). E-S1은 신규파일이 0개인 케이스였고, **이번에 필요한 건 "신규파일 1개 이상"인 케이스의 판정 확장**이다.

### 1-3. 규약안 — "사전등록 화이트리스트 + 집합 완전일치"

```
[사전 조건 — 임포트 전에 완료]
1. art-pipeline이 예상 신규 경로를 raw 문서에 기입하고 git commit (t0 확보)
   예) VFX/T_FX_HolyInitial.uasset
       VFX/T_FX_HolyRepeatable.uasset
       VFX/T_FX_HolyImpact.uasset
       VFX/MI_FX_Holy.uasset          (신규 MI 필요 시)
   → WHITELIST = 이 경로들의 집합(git status 출력과 동일 표기: Content/ 상대경로)

[판정 — 임포트 직후, 기계 실행]
2. git -C D:\unreal\projectTP\Content status --porcelain --untracked-files=all
3. MODIFIED = 코드가 `??`가 아닌 모든 라인 (M/D/R/A 등)
   UNTRACKED = 코드가 `??`인 모든 라인

PASS ⟺ 아래 4개 전부 참
  (a) MODIFIED == ∅                         ← 무예외, 기존 규약 그대로(완화 0)
  (b) UNTRACKED == WHITELIST                 ← 부분집합 아님, 완전 집합일치
  (c) WHITELIST의 모든 경로가 `VFX/`로 시작 ∧ 기존 마스터 머티리얼·BP·DT·레벨 경로와 무교차
  (d) 화이트리스트 commit 시각(t0) < 임포트 파일 mtime  ← 사후 끼워맞추기 방지

FAIL 시: git checkout -- <MODIFIED 경로들> (기존파일 원복)
        + git clean -fd VFX/ 범위 한정 (화이트리스트 밖 신규파일만 제거)
```

### 1-4. ★핵심 질문에 대한 답 — 진짜 위험을 잡는가

**잡는다.** 이유:

- **(a) 무예외**가 살아있는 한 `MI_FX_Smear`/`MI_FX_Hit`·마스터 머티리얼·`DT_Skills`·레벨 등 **기존 공유 자산이 1바이트라도 바뀌면 무조건 FAIL** — 이게 진짜 위험(설계제약2가 막으려던 것)이고 이 규약은 그 부분을 전혀 완화하지 않는다.
- **(b) 완전일치**가 "부분집합 허용"(`UNTRACKED ⊇ WHITELIST` 정도)보다 훨씬 강하다 — **선언 안 한 파일이 몰래 끼면 그 자체로 FAIL**이라, "화이트리스트 뒤에 숨어 추가로 뭔가를 슬쩍 넣는" 시나리오를 차단한다.
- **(c) 경로/유형 스코프**가 화이트리스트 항목 자체의 남용을 막는다 — 예를 들어 화이트리스트에 `M_Sprite_Flipbook_Lit.uasset`(마스터 머티리얼) 같은 민감 경로를 끼워 넣는 것 자체를 "새 파일"이라는 이유로 승인해줄 수 없게 한다.
- **(d) 시각 순서**가 "결과 보고 나서 화이트리스트를 결과에 맞춰 쓰는" 사후 합리화를 차단한다 — 이게 없으면 (b)의 강함이 무의미해진다(뭐가 생기든 그걸 화이트리스트라고 우기면 통과).

**구멍이 되는 조건(반드시 지켜야 할 2가지)**: (b)를 "부분집합"으로 완화하거나 (d)를 생략하면 이 규약은 즉시 무력화된다 — 이 둘이 이 규약의 유일한 방어선이다. S5 구현 시 verifier가 **이 2가지를 TC로 명시 검증**할 것을 권고(예: 화이트리스트 외 파일 1개를 의도적으로 섞어 FAIL 재현하는 자가시험 — [[자율진행_plan_v1]] B2 오라클-diff 비교기와 같은 패턴).

**plan 반영 형태 제안**: 설계제약2 문구를
> *"`Content/` SHA256 manifest diff"*
→
> *"`Content/` git 상태: 기존 추적 파일 변경 0(예외 없음) ∧ 신규 미추적 파일은 **임포트 전 커밋된 화이트리스트와 집합 완전일치**(부분집합 불허, 사후 등록 불허)"*
로 교체 권고.

## 2. ★질문 ② — B4 밀도 범위 0.8~1.3×는 타당한가

### 2-1. 실측 데이터는 정확히 2점, 둘 다 1.0× 미만

| 데이터 | 배율 | 판정 근거 | 신뢰도 |
|---|---|---|---|
| legacy(`Hit Effect 01`/`Smear VFX 01`, 48px) | **0.77×** | `T_FX_Hit`은 지금도 25행이 참조하는 **라이브 프로덕션 자산**([[내장트레일_director판정]] "완전 존치·무접촉") | ★진짜 owner 승인(장기 무이의 배포) |
| 신규 3종(`Free/`, 64px) | **0.58×** | *"미해결"*로 플래그 | ⚠**owner 육안 미실시** — S6가 아직 안 왔다([[E_스파이크_plan]] 판정1: *"답을 미리 아는 게 아니라 찾는 게 실험대의 목적"*). "나쁘다고 확인됨"이 아니라 **"아직 아무도 안 봤음"**이 정확한 상태 |

★**이 자체가 plan의 전제를 한 겹 약화시킨다** — "0.58×는 문제, 0.77×는 무이의"라는 대비는 director 질문이 제시한 틀이지만, 실제로는 **owner 육안 판정이 있는 쪽은 0.77× 하나뿐**이다. 0.58×는 계산상 더 나쁜 숫자일 뿐 시각적으로 "나쁘다"고 확정된 적이 없다. 두 점을 "합격/불합격" 대비로 쓰려면 이 비대칭을 plan에 명기해야 한다.

### 2-2. 하한 0.8×는 legacy 자신을 탈락시킨다 — 자기모순

```
5.00 / 6.48 = 0.7716...
```

**0.7716 < 0.8.** B4 게이트를 "0.8~1.3×에 후보가 있는가"로 그대로 쓰면, **유일하게 실제로 owner 승인을 받은 데이터점(legacy)조차 그 범위 밖**이다. 즉 이 기준은 *"legacy보다 나은 것만 찾아라"*(하한을 legacy보다 살짝 위로)라는 의도라면 성립하지만, 그렇게 읽으려면 **"legacy(0.77×) 자체는 애초에 후보 심사 대상이 아니다"**라는 전제가 plan에 명시돼야 한다 — 지금은 그 전제가 안 적혀 있어 **하한값이 어디서 왔는지 근거가 없다**(director 질문 원문과 동일 지적).

셀 픽셀 단위로 환산하면 더 명확하다(`uu/텍셀 = 240 ÷ 셀px`):

| 배율 경계 | 필요 네이티브 셀(px) |
|---|---|
| 1.0×(완전 정합) | 37.0px |
| 0.8×(plan 하한) | 46.3px |
| **legacy 실측** | **48px → 0.77×** |
| 0.58×(신규 3종, 미해결) | 64px |

**48px(legacy)이 46.3px(plan 하한)보다 크다** — 정확히 저 경계 바로 바깥에 legacy가 있다. 하한을 0.8이 아니라 **0.75~0.77 사이**로 두면 legacy가 자기 자신의 기준을 통과한다.

### 2-3. 상한 1.3×는 실측 0건 — "대칭"이라는 가정이 근거 없음

1.0× 초과(텍셀이 캐릭터보다 굵어 보이는 방향) 실측은 **`Holy VFX 01`의 1.16× 하나뿐**이고, 이것조차 [[_RawAssets_전수카탈로그]] 자신이 명시하듯 **"외삽 계산일 뿐, 실제 임포트·육안 검증 전까지 유력 후보일 뿐 채택 가능 아님"**(§4-3·§10)이다. 즉 **1.0× 위쪽 방향엔 검증된 데이터가 0건**이다.

0.8~1.3×이 1.0×를 기준으로 **비대칭(−0.2/+0.3)**인 것도 근거가 안 보인다 — 만약 "아래쪽 0.77이 괜찮았으니 대칭적으로 위쪽도 그만큼 허용"이라는 논리라면 +0.23이 되어야 **1.23×**이지 1.3×가 아니다. 그리고 애초에 **텍셀이 잘게 보이는 것(0.58~0.77×, 도트가 캐릭터보다 곱게 보임)과 굵게 보이는 것(1.16×↑, 도트가 캐릭터보다 뭉텅하게 보임)은 지각적으로 대칭이라는 보장이 없다** — 전자는 "과하게 정교해 보임", 후자는 "저해상도로 보임"으로 실패 양상 자체가 다르다. 대칭 가정은 검증되지 않은 편의적 추정이다.

### 2-4. 실측 기반 대안 제안

경험적으로 방어 가능한 유일한 문장:

> **"legacy가 서 있는 지점(0.77×, 셀 48px)과 같거나 그보다 1.0×에 가까운 후보는 안전 등급, 그보다 1.0×에서 먼 후보(0.58× 이하 방향)는 기존 미해결 문제와 동일 위험군, 1.0× 초과 방향은 검증된 사례가 없어 후보로 쓰려면 S6에서 반드시 육안 확인이 선행돼야 한다."**

수치 게이트가 굳이 필요하면:

| 축 | 제안값 | 근거 |
|---|---|---|
| 하한(1.0× 미만 방향) | **≥0.75×**(셀 ≤50px 근사) | legacy 실측 0.7716×를 포함하도록 최소 여유만 둠. 0.8은 legacy를 제외해 근거가 없음 |
| 상한(1.0× 초과 방향) | **수치 게이트 없음 — "S6 육안 필수" 플래그로 대체** | 방향 자체가 미검증이라 어떤 상한도 현재 데이터로 정당화 불가. `Holy VFX 01`(1.16×)은 이 조건에서 "게이트 통과"가 아니라 **"조건부 후보, 육안 확정 전까지 미채택"**으로 표기해야 정직함 |

**결론**: B4 게이트 문구 *"밀도 0.8~1.3× 후보 ≥1"*을 *"0.75× 이상 후보 ≥1 **또는** 1.0× 초과 후보(육안 미검증 명시) ≥1"*으로 완화·정정 권고. 아래 §3의 `Holy VFX 01`은 후자(조건부)에 해당한다.
