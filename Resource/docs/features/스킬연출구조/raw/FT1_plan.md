## 1. FT1이 완성되면 무엇이 달라지나 (오너용)

화면상 변화는 **없다.** 게임 플레이도 그대로다. 달라지는 것은 이것이다:

| 지금 | FT1 후 |
|---|---|
| 전투 검증 1회 = **오너가 Start 누르고 스킬·타겟을 수십 번 클릭** | 전투 검증 1회 = **에이전트가 데이터 한 벌을 꽂고 PIE를 켠다.** 클릭 0회 |
| 검증 결과 판정 = 사람이 로그를 눈으로 봄 | **기계가 채점** — 손계산 정답지([[SPD원장_오라클_v1]] §7 20행)와 자동 대조, 다르면 그 행 번호를 찍어준다 |
| FT2~FT8(스킬을 CSV 데이터로 이주하는 수술 7건)의 실증 30건 전부가 오너 세션 대기 | **전부 에이전트 단독 실행** — 오너는 결과 보고만 받는다 |
| "수술 후에도 전투가 안 깨졌나?"를 확인할 방법이 오너 플레이뿐 | 수술 전/후에 같은 데이터로 자동 재생 → **diff 0이면 무회귀 증명** |

한 줄로: **이후 모든 전투 수술(FT2~FT8, 그 뒤 D6 연출·사운드, A2 1000풀)의 검증 단가가 "오너 세션 1회"에서 "에이전트 PIE 1회"로 내려간다.** 그리고 이 장치의 커맨드 주입 통로가 나중에 **PvP 원격 커맨드·AI 봇이 그대로 쓰는 인터페이스**([[알파_개발계획]] 제약 P-2)를 겸한다 — 지금 만들면 한 줄, 나중에 만들면 재작업.

**만들지 않는 것(경계)**: 새 게임 기능 0건. 스킬·연출·UI 변경 0건. 기존 전투 로직 수정 0건(전부 additive 스캐폴드 + 기본값 off 토글).

## 4. 커맨드 주입 인터페이스 (★P-2 반영)

[[알파_개발계획]] P-2: *"커맨드의 데이터화 — '누가 어떤 스킬로 누굴'을 구조화 데이터로 주입하는 통로 유지. FT1의 자동 조작이 사실상 이 인터페이스."*

### 4-1. 커맨드 스키마 (지금 계약으로 확정)

```
커맨드 1건 = { seq: 순번, casterSlot: "A3",  skillId: 31000000, targetSlot: "B2" }
```

- `casterSlot`은 **주입값이 아니라 검증값**이다 — 턴 순서는 게임(SPD 정렬)이 정하므로, MA는 `AwaitCommand` 콜백 시점의 실제 `ActiveUnit`과 기대 `casterSlot`을 대조해 **어긋나면 fail-loud 1줄 후 정지**한다. 턴 순서 드리프트를 그 자리에서 잡는다.
- `targetSlot`은 **명시 주입**([[BT3_MA_상세설계서]] §6 — 게임 자동 타겟팅에 위임하면 "게임이 게임을 채점"하는 순환) — 슬롯ID를 런타임 리졸버(`ResolveSlotToActor`, 신규 작성 — `BP_BattleManager`에 부재 실측)로 액터화해 전달. `NotifyUnitClicked`의 인자가 액터 레퍼런스임은 핀 원문으로 확정됨([[FT1_착수조회_2026-08-12]]).
- 유닛 식별자는 로그와 **같은 표기 계열**(`SpawnPoint_<Team>_<Slot>` ↔ 슬롯 약칭)을 계약서에 못 박는다 — 조인 규칙이 갈라지지 않게.
- **출처 중립**(P-3 정합): 스키마에 "이 커맨드가 사람/AI/원격/재생 중 무엇에서 왔나"를 넣지 않는다 — 같은 통로에 주입자만 바뀌는 구조. 나중에 원격 플레이어·AI 봇이 **이 스키마 그대로** 들어온다.

### 4-2. 저장 형식 — 병렬 배열로 시작, struct 승격은 오너 세션 편승 (비차단)

신규 struct(`F_MaCommandRow`)+DataTable이 정석이나, **struct 신설은 이 프로젝트에서 오너 세션 항목**이다(D5.5 선례). 자율 진행을 막지 않기 위해:

- **1차(지금)**: `BP_BattleManager`에 Instance Editable **병렬 배열 3개**(`MaCasterSlots[]`·`MaSkillIds[]`·`MaTargetSlots[]`, 인덱스 정렬) + 리졸버. 시나리오 20행의 원천은 [[SPD원장_오라클_v1]] §7 — 대조는 손이 아니라 `oracle_diff.py`가 한다.
- **2차(선택, 비차단)**: D5.5 오너 struct 세션에 `F_MaCommandRow` 1건 편승 → DataTable/CSV 승격. **인터페이스(스키마+리졸버 이음새)는 1차에서 이미 확정**되므로 승격은 저장 형식 교체일 뿐 재작업이 아니다 — P-2의 "지금 하면 한 줄"은 이 이음새를 말한다.

## 6. 검증 설계 — 3fps 환경에서 무엇을 어떻게 확인하는가

★**대원칙: 프레임·실시간 기반 판정 전면 금지. 카운트·순서·논리값·diff 기반만.** 에이전트 PIE는 tick rate 3으로 떨어지고 바꿀 수 없다(함정100). 이 하네스의 모든 게이트는 그 제약 안에서 설계됐다:

| 판정 축 | 3fps 내성 | 방법 |
|---|---|---|
| 원장 대조(MA-1a) | ✅ 완전 | `dmg`/`hp`/`died`는 **논리 결과**라 tick 무관. `oracle_diff.py`(자가시험 32/32 PASS 확인, 2026-08-13 실조회) 전 행 diff |
| 발화 카운트 | ✅ 완전 | `SessionBoundary\|` 1줄 · `StartBattle` 1회 · `PlayAttack enter n == exit n` — 카운트는 tick 무관(FT1-0_TC 확정 원칙) |
| 순서(경로) | ✅ 완전 | State 토큰 **시퀀스**(`INIT→TurnStart→AwaitCommand→…`) — 순서는 tick이 늦춰도 바뀌지 않는다 |
| 무회귀(정적) | ✅ 완전 | 수술 전/후 핀 원문 diff — PIE 자체가 불요 |
| 타이밍 **값** | ❌ **판정 금지** | `t=`·Δt는 3fps에서 ~333ms 양자화 — **기록만 하고 판정 근거로 쓰지 않는다**(보고서에 `max tick rate` 명기 의무). 타이밍 값 판정이 필요한 항목(MA-1b 등)은 오너 60fps 세션으로 이월 |

- **재사용(신규 구현 최소)**: `battle_log` 패키지(parser·session·tokens·oracle) + `oracle_diff.py` + `battle_log_selftest.py`를 그대로 쓴다. 파싱 구현은 리포에 1곳 원칙 유지 — **신규 파서 금지.**
- **신규는 등록뿐**: `SessionBoundary\|`·`PlayAttack\|`·`SkillSelected\|`·`MA:AUTOSTART` 계열을 `tokens.py`(SSOT)에 등록 + selftest 케이스 추가 + [[전투로그]] §3 표 재생성(AT4-pre의 `STGNOROW`/`RESOLVE` 등록과 같은 절차).
- **세션 키 = `(sid, INIT 발생 순번)`** 을 계약서에 명문화 — 1 PIE 안에서 전투 재시작 시 원장 2벌이 섞이는 것을 막는다(FT1-0_TC 지적 수용).
- 벽시계 시간은 3fps에서 늘어나지만 **판정과 무관**하다 — 소요 추정치는 적지 않는다(근거 없는 수치 금지 선례).
