3. **모든 5행이 동일 결함을 갖고 있다** — legacy 3행(`63000100/200/300`)뿐 아니라 `63000400/500`도 동일 패턴(`/Game/VFX/T_FX_...`, 서픽스 없음). `PlayVfx`가 이번 세션 전에 **단 한 번도 성공 경로를 탄 적이 없다**는 결론은 유지되지만, 원인은 (b)3fps도 (d)배선결함도 아니고 **데이터 포맷**이었다.
4. **작업2 — FT1 핀 원문 확보(조회 전용)**: `EnterAwaitCommand`/`EnterAwaitTarget` 둘 다 Function Graph, latent 노드 0개, 말단 단일 종단 확인(BT3 §3 "Delay 0" 가정과 일치). 단 ★**말단이 조건부 분기(`IsValid(HUDRef)`) 안에 있다**는 새 발견 — BT3 설계가 몰랐던 부분. `StartBattle()`은 ★**재진입 가드가 전혀 없다**(`BattleState` 체크 없이 무조건 `SortTurnQueueBySpd → EnterTurnStart` 실행) — [[BT3_MA_상세설계서]] §9-4 우려가 실측으로 확정됨.
5. **규율**: `BP_BattleManager`/`BP_BattleSpawnPoint` 조회만(0건 수정, `is_dirty` 전 구간 false 확인). `BP_FxLabQuad`는 테스트 트리거 배선 후 원상복구(`get_node_infos` 전/후 동일 확인) + 재컴파일 + 저장(`de62a27`류 논리단위 커밋). `DT_Vfx`는 값 원복 확인, 저장은 최종적으로 diff 0(git status 공백). `max tick rate 3` 재확인(함정100과 일치). push 안 함.

  ```
  PlayVfx(63000100) → Delay(0.3) → PlayVfx(63000200) → Delay(0.7)
  → PlayVfx(63009999,fail-loud) → Delay(0.8) → PlayVfx(63009001,제거된행) → Delay(0.3)
  ```

  이 노드들 자체는 온전했다 — E-S2가 `break_pins`로 **호출 진입점만** 끊어놨었다(`CallFunction_65`의 execute/self 핀 미배선).

### 트리거 배선(임시) — 정확한 삽입 지점

`ReceiveBeginPlay`의 기존 초기화 체인을 먼저 추적했다(끝까지):
```
BeginPlay → CreateDynamicMaterialInstance(MI_FX_Smear) → SetMid → SetMaterial(Quad, Mid)
→ SetVisibility(false) → SetCollisionEnabled(NoCollision) → [기존 종단]
```
★**주의사항 하나 확보**: 처음 `connect_pins`로 `BeginPlay.then`을 `TestDriver_TEMP` 호출 노드에 직접 이었더니 **기존 연결(CreateDynamicMaterialInstance 체인)이 대체되어 끊겼다** — 이 MCP의 `connect_pins`는 출력 실행핀의 기존 배선을 **덮어쓴다**(fan-out이 아니라 교체). 그대로 뒀다면 `Mid`가 `None`인 채 `PlayVfx`가 실행돼 원인이 뒤섞인 거짓 결과가 나올 뻔했다 — 즉시 원복하고, **진짜 종단**(`SetCollisionEnabled.then`, 기존에 미배선)에 새로 이었다. carve-out 방식(AT4-b의 FT1-1b 설계와 동형)으로 기존 초기화 로직 100% 보존.

### 원인 특정 — `PlayVfx` 함수 그래프 추적

`PlayVfxInternal`(EventGraph Custom Event) 내부 체인:
```
GetDataTableRow(DT_Vfx) → BreakFVfxRow → texPath(String, 스키마 확인: type=string, SoftObjectPath 아님)
→ MakeSoftObjectPath(PathString=texPath) → ToSoftObjectReference → AsyncLoadAsset(Asset)
  Completed → CastToTexture2D(Object)
    CastFailed → FXLAB:TEXMISS  ← ★여기로 빠짐
    then → SetTextureParameterValue... → FXSHOW
```
배선 자체는 AT4-b가 확인한 대로 `Completed`에 정확히 물려 있다(재확인, (d) 갈래 배제 유지). `DT_Vfx.get_schema` 결과 `texPath`는 `{"type":"string"}` — 즉 raw `FString`이고, DB에 저장된 값이 `"/Game/VFX/T_FX_Smear"`처럼 **패키지 경로만 있고 `.오브젝트이름` 서픽스가 없다**. `FSoftObjectPath`는 `Package.Object` 형식을 기대하므로, 서픽스 없는 문자열로는 오브젝트를 정확히 못 찾아 `AsyncLoadAsset`의 `Object` 출력이 유효한 `Texture2D`로 리졸브되지 않고 `CastToTexture2D`가 실패한다.

참고로 같은 그래프의 하드 레퍼런스(`CreateDynamicMaterialInstance`의 `SourceMaterial` 핀)는 `"/Game/VFX/MI_FX_Smear.MI_FX_Smear"`처럼 **정확히 서픽스가 붙어** 있다 — 하드 레퍼런스는 에디터가 자동으로 완전한 경로를 채워주지만, `DT_Vfx`의 `texPath`는 balance/디자인 쪽에서 **문자열로 손으로 입력**한 값이라 서픽스가 빠졌다.

## 작업2 — FT1 착수용 조회 2건

★규율: `BP_BattleManager` **조회만**(`find_nodes`/`get_node_infos`), 수정 0건. 전 구간 `is_dirty=false` 확인.

### 2-1. `EnterAwaitCommand` / `EnterAwaitTarget` 핀 원문

둘 다 **Function Graph**(BT3 §2 가정과 일치, F7b v2 실측 계승 성립).

**`EnterAwaitCommand` 실행 체인**(전수 추적):
```
FunctionEntry → SetBattleState(2) → PrintString("State:AwaitCommand:t={0}")
→ SetbInputLocked(false) → ForEachLoop(TurnQueue)
    [LoopBody: IsValid(unit) → HighlightOff(unit)]
    Completed → SetSelectedTargets([]) → HideAll(ButtonRef) → IsValid(HUDRef)
        [Is Valid  → SetActiveUnit(Menu_SkillMenu, ActiveUnit) → SetVisibility(Menu_SkillMenu, Visible) → (then 미배선, ★종단)]
        [Is Not Valid → (미배선, 죽은 분기)]
```

**`EnterAwaitTarget` 실행 체인**(전수 추적):
```
FunctionEntry → SetBattleState(3) → PrintString("State:AwaitTarget:t={0}")
→ ResolveTargetPool(TargetToken=PendingTargetToken, Caster=ActiveUnit) → ForEachLoop(ReturnValue)
    [LoopBody: HighlightOn(element)]
    Completed → ShowCancel(ButtonRef) → IsValid(HUDRef)
        [Is Valid  → SetVisibility(Menu_SkillMenu, Collapsed) → (then 미배선, ★종단)]
        [Is Not Valid → (미배선, 죽은 분기)]
```

**latent 노드**: **0개**(둘 다) — `PrintString`/`SetVariable`/`ForEachLoop`매크로/`IsValid`매크로/직접 함수호출 전부 즉시 실행. `Delay`/`RetriggerableDelay`/`Timeline` 없음. **[[BT3_MA_상세설계서]] §3 "MA Delay 0" 규약이 이미 충족된 상태**(위반 사례 없음, 앞으로 안 넣으면 됨).

★★**BT3가 놓친 발견 — 종단이 조건부 분기 안에 있다.** 두 함수 모두 "말단 1노드"라고 부를 수 있는 지점(`SetVisibility(Menu_SkillMenu, ...)`)이 **`IsValid(HUDRef)`의 `Is Valid` 분기 안**에 있다. `Is Not Valid`는 완전히 미배선(죽은 분기, fallback 없음). 즉 `HUDRef`가 어떤 이유로든 무효라면:
1. 이 종단 노드 자체가 실행되지 않는다
2. BT3가 여기 붙이려는 MA 훅(`CustomEvent_MA_OnAwaitCommand`/`OnAwaitTarget` 호출)도 같이 스킵된다

이는 현재 정상 흐름에서는 `HUDRef`가 항상 유효할 것으로 추정되어 문제가 안 될 가능성이 높지만(레벨에 HUD가 항상 배치돼 있다면), FT1-1a 구현자가 "말단 = `IsValid` 분기 밖의 무조건 실행 지점"을 원한다면 실제로는 **`HideAll(ButtonRef).then`**(`EnterAwaitCommand`) / **`ShowCancel(ButtonRef).then`**(`EnterAwaitTarget`) — 즉 `IsValid(HUDRef)` 매크로 진입 **직전**이 더 안전한 후보다. [[BT3_MA_상세설계서]] §4-4 "말단에 정확히 1노드" 화이트리스트를 확정할 때 **어느 지점을 "말단"으로 볼지**를 qa-critic/PM이 판단해야 한다(설계 판단이라 임의로 정하지 않고 여기 보고만 한다).

**부가 확인**: `State:AwaitCommand:t={0}` / `State:AwaitTarget:t={0}` 리터럴 포맷이 이미 실재한다(`FormatText` 노드 원문에서 직접 확인) — MA-1b(경로 동치, 상태 전이 토큰 시퀀스 비교)가 참조할 상태 토큰 포맷이 [[BT3_MA_상세설계서]] §10 미확인#5(LOG-A 4bool 커버리지)와 별개로 **최소 이 두 상태는 이미 로그 문자열을 갖고 있음**을 실증. (`bPrintToScreen=false`/`bPrintToLog=true`이므로 화면엔 안 뜨고 로그 파일에만 남는다.)

### 2-2. `StartBattle()` 재진입 가드

**`StartBattle` 전체 그래프(3노드, 전수)**:
```
FunctionEntry → SortTurnQueueBySpd(self) → EnterTurnStart(self) → (then 미배선, 종단)
```

★★**가드 없음 — 확정.** `BattleState` 체크·`Branch`·`IsValid` 등 **어떤 조건 분기도 없이** 매 호출마다 무조건 `SortTurnQueueBySpd` → `EnterTurnStart`를 실행한다. [[BT3_MA_상세설계서]] §4-2/§9-4가 "미확인"으로 남겼던 우려가 그대로 사실로 확정됐다 — **`StartBattle()`이 두 번 호출되면 진행 중인 배틀 상태와 무관하게 턴 큐를 재정렬하고 턴 시작 로직을 다시 태운다.**

**FT1-1b(자동 시작 토글) 설계에 대한 함의**: [[BT3_MA_상세설계서]] §4-2가 권고한 `bAutoStartBattle` 토글이 실수로 두 번 발화하거나(`BeginPlay`가 두 번 불리는 상황, 또는 레벨 재로드), 오너가 수동으로 Start 버튼을 누른 후에 자동 토글도 발화하는 식으로 **경합**하면 `StartBattle()`이 무방비로 재진입되어 턴 큐 재정렬이 배틀 중간에 발생한다. → [[BT3_MA_상세설계서]] §9-4 미확인을 "가드 없음, 확정"으로 닫는다. **FT1-1b 구현 시 `bAutoStartBattle`의 커스텀 이벤트 내부에(또는 그 직전에) `BattleState==0` 등 자체 가드를 반드시 넣어야 한다**(BT3 원안이 권고한 방향, 실측으로 뒷받침됨).
