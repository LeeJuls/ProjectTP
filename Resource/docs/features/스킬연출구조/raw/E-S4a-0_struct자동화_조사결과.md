# E-S4a-0 — struct 편집 자동화 가능성 조사

> 상위: [[E_스파이크_plan]] · 영향: [[D5.5_오너_struct세션_절차서]] §2차 ④ · 관련: [[언리얼_MCP_실전노하우]]

## 왜 조사했나

E단계 plan 확정 직전 qa가 **원안의 전제를 뒤집었다**(E-M5).

> 원안: *"MCP 토큰셋에 struct 편집 툴이 없다 → struct 편집은 오너 수동 GUI뿐"*

**"MCP 툴셋에 없다"는 참이지만 그것이 "자동화 불가"를 의미하지 않았다.** TAPython의 `PythonStructLib`가 **2026-07-16에 `F_SkillsRow`를 15→23필드로 실제로 확장한 전례**가 있었다(`Content/Python/f7b_struct_bootstrap.py`). MCP 경로와 Python 경로는 **별개**다.

→ 오너 세션 횟수가 걸린 문제라 **S4a 앞에 조사 단계를 신설**했다.

## ★Director 판정 — **스크립트 경로 채택**

**근거는 "빠르다"가 아니라 "오류가 침묵하지 않는다"이다.**

GUI 타이핑의 실패 모드는 [[D5.5_오너_struct세션_절차서]] 공통주의 ③에 이미 적혀 있다:

> *"철자가 틀리면 **조용히 매칭 실패**하고 기본값이 들어간다"*

`fxProjectileId`를 `fxProjectilId`로 치면 **에러가 안 뜬다.** CSV 임포트가 그 컬럼을 못 찾고 `0`을 넣는다. 그리고 `0`은 이 스키마에서 **"즉발(투사 없음)"이라는 유효한 값**이라 다운스트림에서도 안 걸린다. 6필드 × 오너 수동 타이핑은 이 위험을 6번 반복한다.

스크립트는 **사전/사후 필드명 집합을 비교해 유실을 감지하면 저장 자체를 중단**한다. 실패가 시끄럽다.

**기각한 대안**: GUI 유지 — "스크립트 결함 2건을 고치느니 그냥 치는 게 빠르다"는 판단도 가능하지만, **6필드 전부가 FK 정수라 오타의 대가가 무음 폴백**이다. 수정 비용(2곳)이 그 위험보다 싸다.

## ★선행 조건 — 결함 2건 수정 (실행 전 필수)

### 결함 1 — 멱등 가드 과광범위 ★**지금 실제로 막는다(확정)**

`already_bootstrapped()`가 **`F_StatusEffectRow.uasset` 존재 여부만** 보고 `main()` **전체를 SKIP**한다. 그 애셋은 이미 있다. → **지금 그대로 돌리면 아무 일도 일어나지 않는다.**

추가로 `SKILLSROW_NEW_FIELDS` 상수가 **2026-07-16 당시의 8필드로 박혀** 있다. 이번 6필드로 교체해야 한다.

→ **최소 2곳 수정.**

### 결함 2 — `names[-1]` 가정

`get_guid_from_friendly_name()`이 실패하면 폴백으로 *"필드명 목록의 마지막 = 방금 추가한 필드"*로 간주한다. **7월 실행에서 이 폴백이 실제로 발동했는지는 확인 불가**(로그 로테이션으로 소실).

이번에 **6번 더 타므로** 재사용 전 수정 권장 — `add_variable()` **전후 집합 차분**으로 결정론적 식별.
