★**PM/director 판정 권고**: **"BP 생성 가능" 쪽으로 잠정 채택**하고 `sid=<Now>-<Rand>` 산식으로 진행. **완전한 실측 확정(create+즉시delete 1회)은 S2 착수 첫 스텝**에서 닫을 것 — 이 시점엔 이미 "수술" 단계이므로 예외 제약이 없다.

## 3. F0p-03 — `PlayAttack` 그래프 형상

### ⓐ Function Graph인가 EventGraph 커스텀 이벤트인가

`list_graphs(BP_BattleSpawnPoint)` → `UserConstructionScript`/`AlignSpriteToCamYaw`/`ResetForBattle`/`EventGraph` **4개뿐** — `PlayAttack`이라는 Function Graph는 **없다**.
`list_events(BP_BattleSpawnPoint)`에서 `PlayAttack`: `{"description":"커스터마이저블한 이름과 파라미터가 있는 이벤트입니다.","bIsImplemented":true}` — 커스텀 이벤트로 확인.
`find_nodes(EventGraph, title="PlayAttack", entry_points_only=True)` → `EventGraph.K2Node_CustomEvent_0`, `type_id="AddEvent|Custom|PlayAttack"`.

★**확정: EventGraph 커스텀 이벤트다(Function Graph 아님).**

### ⓑ latent 노드 존재 여부

`get_connected_subgraph(K2Node_CustomEvent_0)` → 37개 노드. 그중:
```
EventGraph.K2Node_CallFunction_17 | 유틸리티|플로컨트롤|RetriggerableDelay
```
★**확정: `RetriggerableDelay` 실재.**

### ⓒ exec 종단 개수 + 구조

exec 핀 연결을 전수 추적한 결과, 흐름은 다음과 같다:

```
CustomEvent_0(PlayAttack).then
  → MacroInstance_1(IsValid)
      .IsNotValid → ★DANGLING(종단1, guard-fail 조기종료)
      .IsValid → CallFunction_13(SetScalarParameterValue) → GetDataTableRow_1(DT_Motions)
          .then(Found)      → VariableSet_18(SetPendingFrameCount) ─┐
          .RowNotFound      → VariableSet_19(SetPendingFrameCount) ─┤→ IfThenElse_8(Branch, execute에 2 conns 합류)
                                                                      .then → VariableSet_20 ─┐
                                                                      .else ──────────────────┤→ CallFunction_14(SetScalar, execute에 2 conns)
                                                                                                → CallFunction_15(SetScalar)
                                                                                                → ExecutionSequence_0(Sequence)
                                                                                                    .then_0 → CallFunction_17(RetriggerableDelay)
                                                                                                        → CallFunction_18/19/20(SetScalar ×3) → ★DANGLING(종단2, Delay 이후 완료)
                                                                                                    .then_1 → IfThenElse_10(Branch)
                                                                                                        .then → CallFunction_117(SetWorldLocation) → ★DANGLING(종단3, 즉시 이동완료)
                                                                                                        .else → ★DANGLING(종단4, 즉시 무이동종료)
```

★★**확정: exec 종단 4갈래.** `Sequence`(`ExecutionSequence_0`) 노드가 `then_0`(RetriggerableDelay 경로)과 `then_1`(위치갱신 Branch 경로)로 **동시에** 갈라진다. UE Blueprint의 `Sequence`는 같은 프레임에 순차 호출하되, `then_0` 쪽이 latent(`RetriggerableDelay`)에 걸리면 **그 자리에서 실행이 정지하고 `then_1`은 같은 프레임에 즉시 이어서 실행된다** — 즉 한 번의 `PlayAttack` 호출에서 "즉시 완료되는 가지"와 "일정 시간 뒤 완료되는 가지"가 **동시에, 독립적으로** 존재한다.

### "exit 로그를 어디에 두면 무엇을 재는가" — 1문장 확정

★**Then_0(RetriggerableDelay 경로) 말단(`CallFunction_20.then`)에 두면 "스미어 셰이더 파라미터가 실제로 복원되는 시각(Delay 만료 후)"을 재고, Then_1(Branch/SetWorldLocation 경로) 말단(`CallFunction_117.then` 또는 `IfThenElse_10.else`)에 두면 "이펙트 쿼드 위치 갱신이 완료된 시각(같은 프레임, 지연 없음)"을 잰다 — 이 둘은 서로 다른 사건이며, guard(IsValid) 통과 시 1회 `PlayAttack` 호출마다 정상적으로 exit가 2회(종단2+종단3 또는 종단2+종단4) 발생하고, guard 실패 시 1회(종단1)만 발생한다.**

### 판정 — S5(0b) 설계에 대한 파급 (★계획 수정 필요)

[[FT1-0_TC]] `AU-F0b-01`의 PASS 기준 *"`phase=enter` n == `phase=exit` n"*은 **latent 재진입 경합이 없어도 구조적으로 성립하지 않는다.** 4개 종단에 각각 `branch=guard_fail|delay_end|move_end|nomove_end` 같은 구분 필드를 넣고, 게이트를 **"enter n == guard_fail n + (delay_end n' + (move_end 또는 nomove_end) n'')"** 형태로 재정의해야 한다. 이 발견은 §5-S5 착수 전 plan/TC 갱신이 필요한 사항이므로 PM 보고 대상이다(§4).

## 4. F0p-04 — `bPrintToLog` 핀 연결 프로브(유일한 수술 예외, 연결→즉시원복)

### 대상
`BP_BattleManager.NotifyAttackButtonClicked.K2Node_CallFunction_2`(PrintString, 리터럴 `"NotifyAttackButtonClicked: BLOCKED (bInputLocked=true)"`)의 `bPrintToLog` 입력 핀(index 3). 소스로 **같은 그래프에 이미 존재하는** `K2Node_VariableGet_0`(`GetbInputLocked`, bool 출력)을 재사용 — **신규 노드 생성 0건**, 데이터 핀 fan-out만 사용(§6 line129 "데이터 핀은 fan-out 가능" 확정 사실 재활용).

### 1) 연결 전 핀 원문
```
CallFunction_2.input_pins[3]: name=bPrintToLog, type_id=부울, value="true", connected_pins=[]
VariableGet_0.output_pins[0]: name=bInputLocked, type_id=부울, value="false",
    connected_pins=[{IfThenElse_0, EGPD_Input, index_id=1}]   ← 기존 연결 1건
```

### 2) 연결 시도
`connect_pins(output={VariableGet_0, EGPD_Output, 0}, input={CallFunction_2, EGPD_Input, 3})` → 정상 반환.

### 연결 후 원문(검증)
```
CallFunction_2.input_pins[3]: name=bPrintToLog, value="true",
    connected_pins=[{VariableGet_0, EGPD_Output, 0}]   ← ★연결됨으로 표시
VariableGet_0.output_pins[0]: connected_pins=[
    {IfThenElse_0, EGPD_Input, 1},   ← 기존 연결 유지(끊기지 않음)
    {CallFunction_2, EGPD_Input, 3}  ← 신규 연결 추가(fan-out)
]
```
★★**핵심 확정: MCP `connect_pins`로 advanced 핀(`bPrintToLog`)에 실제로 연결이 성공하고, `get_node_infos`가 그 연결을 정확히 반영한다.** 노하우 문서가 "실증 기록 없음"으로 남겼던 PLAUSIBLE 리스크가 해소됐다 — LOG-A 카테고리 bool 체계(핀 연결 방식)는 **API 차원에서 실행 가능**하다.

### 3) 즉시 원복
`break_pins(output={VariableGet_0, EGPD_Output, 0}, input={CallFunction_2, EGPD_Input, 3})` → 정상 반환.

### 4) 원복 후 재덤프(연결 전과 동일함을 실증)
```
CallFunction_2.input_pins[3]: name=bPrintToLog, value="true", connected_pins=[]   ← 연결 전과 동일
VariableGet_0.output_pins[0]: connected_pins=[{IfThenElse_0, EGPD_Input, 1}]      ← 연결 전과 동일(1건만)
```
★**연결 전/후 핀 원문 완전 일치 실증됨.**

### 5) 부가 확인(사양 외, 안전 범위 내)
원복 후 `compile_blueprint(BP_BattleManager)` 1회 호출 → 예외 없이 정상 반환(컴파일 에러 0). `save_assets` 호출 **0회**.

## 6. §10-1 — MCP로 배열 변수 기본값 대량 설정 가능 여부

### 조사(수술 없이 API 존재·시그니처만)
`BlueprintTools`에 "변수 기본값 설정" 전용 툴은 **없다**(`add_variable`/`set_variable_category`/`set_variable_replication`/`set_variable_instance_editable`는 있으나 값 자체를 세팅하는 툴은 없음). `set_pin_value`/`get_pin_value`는 **그래프 내 노드의 핀**을 대상으로 하며, "MyBlueprint 패널의 클래스 변수 기본값"은 그래프 핀이 아니라 **CDO(Default Object)의 프로퍼티**이므로 대상이 다르다.

대신 `get_default_object(blueprint)` → CDO 오브젝트 레퍼런스 반환 → `ObjectTools.set_properties(cdo, json값)`으로 CDO의 프로퍼티(배열 포함)를 세팅하는 경로가 **구조적으로 존재**한다(`set_properties`의 `values`는 임의 JSON 문자열이라 배열 리터럴도 문법상 허용됨).

### 판정 — 메커니즘 존재, 미실측, 리스크 명시
★**"가능하다/불가하다" 확정은 하지 않는다(지시대로 실제 세팅을 시도하지 않았음).** 근거 있는 위험만 기록:
- 함정③/⑪/(55)가 **"여러 스칼라/구조체 필드를 한 번의 `set_properties` 호출로 동시에 지정하면 일부만 반영될 수 있다"**를 3회 독립 확정했다 — 배열 3개(`MaCasterSlots`/`MaSkillIds`/`MaTargetSlots`)를 한 호출에 몰아넣는 것은 **고위험**.
- 배열 "20행"이 단일 프로�터티(예: `TArray<FString> MaCasterSlots`)라면 그 자체는 "필드 1개"이므로 함정③의 다중필드 문제는 비켜갈 수 있으나, **3개 배열을 한 호출에 같이 넣으면(3필드)** 문제 재현 가능성 있음.
- **권고(안전한 순서)**: 배열마다 **개별 `set_properties` 호출**(3회 분리) + 매 호출 후 `get_properties`로 반영 여부 재확인. 그래도 실패하면 **`MakeArray` 리터럴 노드 폴백**(계획이 이미 준비한 안전망, additive 범위 내).

## 7. §10-3 — `ResolveSlotToActor` 슬롯 원천

### 조사
- `list_variables(BP_BattleManager)` → 29개 변수 전체(`BattleState`/`bInputLocked`/`CurrentIndex`/`RegisteredCount`/`TurnQueue`/`ActiveUnit`/... 등). **슬롯 인덱스 배열(`PartySlots[]`/`EnemySlots[]`류)은 없다.**
- `list_variables(BP_BattleSpawnPoint)` → 29개 변수(`bIsParty`/`JobId`/`Hp`/`CharName`/... 등). **"A3"/"B2" 같은 슬롯 라벨·인덱스 필드는 없다**(팀 구분은 `bIsParty` bool 하나뿐).
- `get_connected_subgraph(RegisterUnitReady.FunctionEntry)` → 이 함수는 **파라미터가 없다**(`input_pins: []`). 내부 로직은 `RegisteredCount`를 1 증가시키고 8이 되면 `InitBattle()`을 호출할 뿐 — **호출한 SpawnPoint 자신의 레퍼런스를 Manager에 전달하거나 저장하지 않는다.**
- `find_actors(name="SpawnPoint")` → 레벨(`map_battle_octopath`)에 `BP_BattleSpawnPoint_C_{0,2,3,4,5,6,7,9}` 8개 인스턴스 확인.
- `get_properties(BP_BattleSpawnPoint_C_9, ["tags","charName","bIsParty"])` → `{"tags":[],"charName":"이름7","bIsParty":true}` — **Tags 배열도 비어있다.**
- `ObjectTools.get_properties(..., ["ActorLabel"])` → 에러(`could not be read: ActorLabel`) — 액터 Outliner 표시 라벨은 이 API 경로로 조회 불가(미확인으로 유지).

### 판정 — ★계획의 두 가설 모두 불충분, 신규 미확인 발견

[[FT1_plan]] §10-3이 던진 질문("Manager 보유 배열인가 vs 레벨 8기 액터 열거인가")에 대해 **"Manager 보유 배열"은 확정적으로 아니다**(그런 배열이 없음, list_variables로 완전 확인). 그런데 **"레벨 8기 액터 열거"만으로도 충분하지 않다** — 열거해도 각 액터가 "자신이 A3인지 B2인지"를 말해주는 데이터가 **`bIsParty`(팀만 구분) 외에는 전혀 없다.** Tags 비어있음, 전용 SlotId 필드 없음, ActorLabel은 이 세션에서 조회 자체가 안 됨(레벨 에디터 Outliner 라벨에 슬롯이 인코딩돼 있을 가능성은 남아있으나 **API로 실증하지 못했다**).

★**PM 보고 필요**: `ResolveSlotToActor` 신규 함수는 계획이 가정한 것보다 설계 범위가 크다. 다음 중 하나가 **S4 착수 전에 결정**돼야 한다:
1. 레벨 액터 **Outliner Label**에 실제로 슬롯이 인코딩돼 있는지(예: "SpawnPoint_Party_A3") — 이번 세션 API로는 못 봤으나 오너가 에디터에서 육안 확인하거나, 다른 조회 경로(SceneOutliner 전용 API 등)로 닫을 수 있음.
2. 없다면 **위치 기반 정렬 규칙**(예: `bIsParty` 그룹별로 X/Y 좌표 정렬 → 인덱스로 A1~A4/B1~B4 매핑) 채택.
3. 최후 수단으로 `BP_BattleSpawnPoint`에 **`SlotId`(FString/Enum) 프로퍼티 신설 + 레벨 8기 개별 세팅**(이 자체가 별도 "수술"이며 S4 범위 확대 항목).

## ★PM 검증 (2026-08-13, append — 위 조사 내용은 수정하지 않았다)

### ⓐ §10-3 "슬롯이 어디에도 없다" → ★**반증. 슬롯은 런타임에 실재한다**

조사자가 마지막에 남긴 가설(*"Outliner Label에 인코딩돼 있는지 확인이 우선"*)이 **맞았다.** PM이 실제 로그로 실증했다:

```
BattleLog|turn=5|attacker=SpawnPoint_Party_A1|target=SpawnPoint_Enemy_B3|action=31000000|dmg=34|hp=46
BattleLog|turn=3|attacker=SpawnPoint_Party_A4|target=SpawnPoint_Enemy_B4|action=32001000|dmg=65|hp=15|effect=ATK_DOWN
```

★**`SpawnPoint_Party_A1` · `SpawnPoint_Enemy_B3` 가 라이브 로그에 그대로 찍힌다.** [[전투로그]] §계약이 규정한 `SpawnPoint_<Team>_<Slot>` 1형식과 일치한다.

→ ★**판정 수정**: *"`ResolveSlotToActor` 설계 범위가 계획보다 크다"*는 **과대평가**였다. 슬롯 문자열은 **이미 존재하고 이미 로그가 쓰고 있다.** 남은 것은 *"그 문자열을 무엇이 만드는가"*(액터 이름 / 표시명 / 조합) **1회 조회**뿐이며, ★**S4 착수를 차단하지 않는다.**
⚠ 단 조사자가 `list_variables`·`get_properties(tags)`에서 못 찾은 것은 **사실**이다 — 그러므로 원천은 **변수가 아니다.** S4 첫 스텝에서 `unit=` 문자열 생성 노드를 역추적해 확정하라.

### ⓑ F0p-03 "exec 4갈래로 exit 2회" → ★**타당하나 미실증(정적 예측)**

PM이 라이브 로그를 조회한 결과 ★**`PlayAttack|` 토큰은 enter 0건 / exit 0건**이다 — **0b가 아직 안 심어졌으므로 당연하다**(S5 작업).

→ 즉 이 결론은 **그래프 정적 분석에 근거한 예측**이지 실측이 아니다. ★**예측은 타당하다**(`ExecutionSequence_0`의 `then_0`/`then_1` 동시 분기는 핀 원문으로 확인됨). 그러나:
