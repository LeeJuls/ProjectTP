# 로그 시스템 개선 plan

> 오너 지시: *"로그 상태 점검"* → [[로그시스템_점검_2026-08-12]] → *"이 방향으로 어떻게 만들지 우선 계획부터"*
> **director 4차 소집 판정.** ★새 트랙을 만들지 않는다 — [[자율진행_plan_v2]]에 **용해**된다.

## ★총판정

> **ⓐ BT2 확장(지금, 오프라인) + ⓑ FT1 선두에 로그 스캐폴드(FT1-0) 편입(S1 봉인 후).**
> 그리고 **②의 순환은 실재하지 않는다.**

## 1. ★순환 판정 — 없다

**PM이 제기한 순환**: *"마커가 있으면 S1 증거 품질↑ / 마커를 넣으려면 S1 봉인이 먼저"*

**→ 판정: S1은 마커 없이 유효하다. 순환의 한쪽 변이 소멸한다.**

| # | 근거 |
|---|---|
| **1** | ★**S1 절차가 마커보다 강한 격리를 이미 제공한다.** [[features/전투완성/raw/BT5_S1봉인수단_판별]] §(c) step3이 *"런 직전 에디터 재시작"*을 요구하고, UE는 재시작 시 `projectTP.log`를 백업으로 밀어낸다. **`projectTP-backup-2026.08.10-13.47.58.log`가 롤오버 동작의 물증**이다 → **S1 런의 로그 파일 전체가 그 세션**이다. **파일 경계는 in-log 마커가 도달할 수 없는 격리 수준** |
| **2** | 파일 내부 다중 PIE도 기존 토큰으로 분리된다 — 엔진 `up for play` + 우리 `State\|event=INIT\|mode=FRESH/RESTART` |
| **3** | ★**함정 101의 피해자는 S1형이 아니라 에이전트형 런이다.** 그 사고는 **한 파일에 여러 세션이 누적된** 국면이었다. 재시작-후-1런인 오너 S1은 **발생 조건 자체가 없다** |

→ 마커의 **S1 기여분 = 0**. 진짜 수혜자는 **FT 트랙 내내 반복될 에이전트 다중-PIE**(당장 FT1의 MA-1a 파싱부터)이므로, 마커의 자리는 **S1 봉인 직후·FT1 검증 이전 = FT1-0**이다.

⚠ **부수 조건 1건**: 세션 1b 직후 **로그 파일 사본을 즉시 아카이브**할 것(다음 기동이 롤오버로 밀어내기 전에). BT5가 *"S1 관련 세이브포인트는 아직 생성된 적 없다"*고 확인했다.

## 2. FT1 편입 — 합치되 커밋은 분리

**"합침"은 세션·게이트 통합이지 커밋 통합이 아니다.**

| 단계 | 대상 | 커밋·세이브포인트 |
|---|---|---|
| **FT1-0a** | `SessionBoundary` 1줄 — `BP_BattleManager.BeginPlay` | 분리 1 |
| **FT1-0b** | `PlayAttack` 진입/반환 2줄 — `BP_BattleSpawnPoint.PlayAttack` | 분리 2 |
| **FT1-0c** ★ | **스킬 선택 로그** — 오너 질문 반영(§5) | 분리 3 |

**근거**: (i) FT1이 이미 *"3커밋 각각 세이브포인트, 게이트는 하나"* 구조라 **롤백 우려는 커밋 분리로 해소돼 있다** — 따로 가서 얻는 게 없다 (ii) 수술 창구가 **1회로 축소** (iii) ★**FT1 자신이 마커의 첫 소비자다** — `AU-F1-01a`가 에이전트 누적 로그를 파싱하므로 **마커가 선행돼야 함정 101이 구조적으로 닫힌다.** 그래서 `0`이 `1a`보다 먼저다.

### ★★고지 1 — FT1 제약 1에 carve-out이 필요하다

plan v2 §5 제약 1은 *"기존 exec·핀 절단 **0**"*인데, **기존 exec 체인에 `PrintString`을 끼우려면 연결 1개를 끊고 통과 재연결(splice)이 필요할 수 있다.**

**수정 문구(취소선+사유로 보존)**:
> **FT1-0 한정 허용** — (i) 삽입 노드는 `PrintString`·`FormatText` 등 **게임 상태 무영향 노드만** (ii) 절단한 연결은 삽입 노드를 경유해 **동일 순서로 재연결** (iii) 수술 전후 exec 시퀀스가 *"삽입 노드 추가 외 동일"*함을 **핀 원문으로 실증**

★**자율 경계 완화**라 오너 고지 대상이다.

## 3. `extract_battle_log.py` — BT2가 흡수한다

**고치지도 폐기하지도 않는다. 재설계(흡수).**

BT2 비교기 구축 시 **로그 ingestion을 공용 모듈 1개**로 만들고, 스크립트는 그 모듈의 thin wrapper로 개조하거나 supersede 각주 처리.

★**게이트: 리포에 `BattleLog|` 파싱 구현이 정확히 1곳.**

**근거**: 3주간 6개 문서가 *"스크립트 수정 대신 별도 grep"*을 반복한 드리프트의 원인은 **도구가 소비 계약 없이 존재**했기 때문이다. 소비자가 확정된 유일한 파서는 BT2 비교기이므로 **파싱의 단일 소스는 비교기 쪽 모듈**이어야 한다.

**포맷 판정**: 점검 문서 내부 모순(§2-1 colon vs §4-1 pipe) → ★**pipe가 이긴다.** colon 채택 시 신규 파서에 문법 예외가 하나 더 생긴다. **신규 토큰 문법은 BT2 산출물인 "토큰 계약서"가 확정하고 FT1-0은 그대로 심는다** — 이 순서가 **파서-이미터 이중 드리프트를 원천 차단**한다.

## 4. ★`AU-B2-03/04`는 방치가 아니었다 — PM 표현 정정

**plan v2 BT2 게이트에 명시돼 있다.** 방치가 아니라 **발주 큐 순서**다 — BT트랙은 BT5(오너 장바구니 확정) → BT1(오정보 확산 차단) 순으로 소화됐고 BT2·BT3이 다음 차례였다.

점검의 *"방치"* 표현은 **추출기 산출물 3주 정체(사실)**와 **TC 수일 대기(정상 큐)**를 한 문장에 섞은 것이다.

**전수 교차 확인: 고아 TC 없음.** 전 AU-패밀리가 단계에 귀속된다.

⚠ 주의 1건 — **TC 패밀리 번호와 plan v2 단계 번호가 FT 후반에서 어긋난다**(TC `AU-F5` = plan `FT6`, `AU-F6` = `FT7`, `AU-F7` = `FT8`. ④를 2청크로 쪼개며 밀렸다). plan v2는 정확히 참조 중이나 **FT 발주 지시서마다 매핑 1줄 명기** 권고.

### ★★스케줄 통찰 — BT2는 세션 1b의 판정 도구다

S1 봉인 게이트가 *"오라클 §7과 전 행 diff 0"*인데 **그 diff를 계산하는 것이 BT2 비교기**다.

★plan v2 의존 그래프에 `BT2 → FT1`만 있고 **`BT2 → 세션 1b 판정` 엣지가 없다.**

→ **BT2가 1b 전에 완료돼야** 오너 런을 그 자리에서 판정하고 **재런 필요 여부를 즉시 확정**할 수 있다(오너 세션 낭비 방지). **BT2를 지금 발주해야 하는 실질적 이유가 이것이다.**

- **③ → 이월 유지**(director 판정). 발동 조건: **LOG-A 가동 후 실제 diff FAIL 발생 시**. ★단 F7b ④(애플리케이터) 검증 때 *"계수가 먹었나"*를 봐야 하므로 **그 시점에 재평가**
- **부수**: `Align:` **320회**(BattleLog의 9배)가 노이즈인지 LOG-A에서 재확인
