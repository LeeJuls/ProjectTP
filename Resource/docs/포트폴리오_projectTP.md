## 한 줄 소개

> **"옥토패스 트래블러 감성의 4:4 턴제 전투를, 매판 다른 6명의 캐릭터로 드래프트하고 밴픽해서 겨루는 Steam PvP."**

## 🎨 비주얼 아이덴티티 — HD-2D

- **2D 도트 스프라이트 + 3D 라이팅/포스트프로세스**로 옥토패스 트래블러류의 디오라마 룩 구현
- 캐릭터는 **레이어 합성**: 피부·의상·머리·무기·표정 5개 파츠를 알파 오버레이 머티리얼로 실시간 조합
  - 파츠 조합 = 데이터(CSV)일 뿐, 이미지 굽기 불필요 → 나중에 캐릭터 풀을 늘려도 재임포트 없이 확장
- 픽셀퍼펙트 렌더링(Nearest 필터·No Mip) + 캐스트 섀도우로 도트 그래픽의 입체감 확보
- 카메라: 전투 액션마다 **동적 어깨너머(OTS) 컷**으로 타격감 연출

## 게임 방향성 — "오락실형" 드래프트 PvP

**기존 기획(모바일 수집형 가챠)에서 방향 전환**한 결정이었습니다.

| | 수집형(초기안) | 드래프트 단판(현재) |
|---|---|---|
| 캐릭터 | 영구 소장 자산 | 매판 소모, 자산 아님 |
| 플랫폼 | 모바일 라이브 서비스 | Steam 단품 |
| 1인 개발 부담 | 콘텐츠·과금·CS 지속 공급 필요 | 패치 위주, 운영 최소 |
| 서버 | 계정·자산 무결성 관리 | 매칭·판정만(경량) |

**전환 이유**: 1인 개발자가 라이브 서비스를 지속 운영하는 건 현실적으로 어렵다는 판단 → "만들어서 팔고 패치하는" 모델로 스코프를 재설계.

## 핵심 시스템 — "1000개 캐릭터"의 실체

- 겉보기엔 1000명의 고유 캐릭터, 실제로는 **소수 원자의 조합**(액티브 30개 + 패시브 10개)
  - ~~평타 10종 × 공용 스킬 10종 × 직업 스킬 10종 = 10³ = 1000가지 조합~~ → ❌ **2026-08-11 정정**: 캐릭터는 액티브 3슬롯이 아니라 **액티브 3 + 패시브 1 = 4슬롯**을 가진다. `10³=1000` 등식도 폐기됐다 — 원래부터 부등식(≥333)이었고 포지션 게이팅으로 조합 공간은 4,800(목표 1,000 대비 샘플링률 20.8%)이다. 근거: [[features/스킬연출구조/raw/D1_4슬롯구조_확정]] · [[features/스킬연출구조/plan]]
  - 조합 생성은 스크립트로 자동 배치 + 중복 검출(이미 검증된 스프라이트 파츠 합성 스크립트와 동일 패턴 재사용)
- **밸런싱 대상이 1000개가 아니라 원자 40개 안팎**으로 축소 → 1인 개발로 관리 가능한 규모
- 포지션(탱커/딜러/서포터) × 등급(1~3성, 확장 가능한 N단계 구조)이 스탯을 결정하는 축

이 구조 설계는 이미 **밸런스 계산으로 안전성 검증 완료** — 포지션 간 상성이 성립하고, 동급 매치업에서 원킬이 나오지 않는 여유 마진까지 계산해뒀습니다.

## 핵심 시스템 — 전투 (구현 완료)

- **4:4 턴제 전투**, 속도(SPD) 기반 턴 순서 — 화면 상단에 턴 카운터 실시간 표시
- **스킬 5종**: 기본공격 · 베기 · 파이어볼 · 막기 · 치유 (쿨다운 포함)
- **상태이상 2종**(기절·공격력 약화, 확률 발동) + **광폭화**(장기전 시 공격력 누적 증가로 무한 교착 방지)
- 데미지/회복 숫자가 색상 구분(빨강/초록)으로 실시간 표시, 피해·회복·막기 판정에 캐릭터 모션이 각각 정확히 반응

## 데이터 아키텍처

- **CSV → DataTable** 파이프라인이 게임 데이터 단일 출처(SSOT) — 기획자가 스프레드시트로 수치를 만지면 그대로 게임에 반영
- 현재 스킬 판정 로직을 **범용 인터프리터 구조로 리팩터링 중** — "스킬마다 코드를 새로 짜는" 방식에서 "데이터가 곧 스킬"인 방식으로 전환
  - 이 작업이 끝나면 1000개 캐릭터의 스킬 조합을 **코드 추가 없이 데이터만으로** 생성 가능
- 기존 판정 경로를 유지한 채(additive-only) 신규 구조를 병행 구축 → 리팩터링 중에도 게임은 항상 플레이 가능한 상태 유지

## 🤖 개발 프로세스 — "AI 개발팀" 오케스트레이션

이 프로젝트의 가장 차별적인 지점입니다. **혼자 코드를 치는 대신, Claude를 Director로 두고 역할이 분리된 전문 서브에이전트 팀을 지휘**하는 방식으로 개발합니다.

| 역할 | 담당 |
|---|---|
| **Director** (오너 + 메인 세션) | 전체 방향·우선순위·최종 승인 |
| system-ui-designer / balance-designer | 시스템 규칙 설계 / 수치·밸런스 설계 |
| gameplay-engineer / umg-engineer | 전투 로직 구현 / UI 구현 |
| scene-builder / art-pipeline / hd2d-art-director | 무대 배치 / 에셋 가공 / 라이팅·룩 |
| **qa-critic** | 논리적 모순·엣지케이스 적대적 검출 |
| **verifier** | 빌드·실행·실증 검증 |

각 역할은 접근 가능한 도구와 판단 수준이 다른 모델로 명확히 분리됩니다 — 설계·최종판단은 상위 모델, 반복 실행은 실행 특화 모델.

## 🛡 품질 보증 — 이중 검증 체계

같은 산출물을 **성격이 다른 두 검증**이 통과해야 합니다.

1. **qa-critic (논리 검증)** — "이게 어떻게 깨질 수 있는가?"를 적대적으로 찾는다. 코드가 만들어지기 전, 설계 단계부터 개입.
2. **verifier (실행 검증)** — 컴파일 에러 0, 실제 플레이 확인, 로그·화면 증거. "돌아간다"를 직접 실행으로 증명.

**단계별 게이트**: 청사진 → 세부 계획(+ 관련 에이전트 피드백) → 테스트케이스 설계 → [구현 → 검증 → 게이트 통과 판정] 반복 → 전체 회귀 테스트. 한 단계가 증거로 통과하지 못하면 다음 단계로 넘어가지 않습니다.

## 📌 케이스 스터디 — "통과할 수밖에 없는 테스트"를 잡아낸 순간

전투에 속도 기반 턴 순서를 도입하자, 기존 회귀 테스트 기준(23턴짜리 "정답 기록")이 조용히 무효화됐습니다.

- 처음 제안된 해법("새로 한 판 돌려서 그걸 새 정답으로 삼자")을 QA가 스스로 **기각** — "실행 결과를 그대로 정답으로 봉인하면, 그 게이트는 절대 실패할 수 없다. 버그가 있어도 통과한다."
- 대신 **게임 코드를 전혀 참조하지 않고** 전투 공식만으로 새 정답을 독립적으로 3번(기획·Director·QA) 손으로 유도 → 세 결과가 **한 글자도 틀리지 않게 일치**
- 그 과정에서 QA 자신의 첫 주장("턴 순서는 결과에 안 바뀐다")도 **틀렸음을 스스로 증명하고 철회** — 선제 킬로 공격 기회 자체가 사라지는 효과를 놓쳤던 것
- 결과: 23턴이 아니라 **20턴**이 진짜 정답이라는 사실을 실행 없이 계산만으로 먼저 확정

이 프로세스가 이 팀의 기본 태도입니다 — **"돌아갔다"와 "맞다"는 다른 질문**이라는 것.

## 📌 엔지니어링 디테일 — 표시값과 판정값의 분리

작은 것 같지만 실사용에서 바로 드러나는 버그를 사전에 잡은 사례:

- 치유 스킬의 로그 값(회복 원본값)과 **화면에 뜨는 숫자**(실제로 오른 HP)를 분리 설계
- 만피 상태인 아군에게 치유를 쓰면 → 로그는 원본값을 기록하되, 화면에는 정직하게 **"+0"** 이 뜹니다
- 분리하지 않았다면 "만피인데 회복 숫자가 뜬다"는 눈에 보이는 버그가 됐을 지점 — 설계 리뷰 단계에서 사전 차단

## 알파 로드맵 한눈에

```
전투 완성 ✅ ──┐
               ├─→ 캐릭터 코어 → 드래프트(밴픽) → 대기실 → 결과 화면 연결 → 알파 완주
(캐릭터 코어와 독립적으로 먼저 진행)
```

**알파 완주 기준(DoD)**: 외부인이 설명 없이 실행해서 "6장 드래프트 → 밴픽 → 4:4 전투(광폭화 포함) → 결과 → 재대전" 루프를 혼자 완주할 수 있어야 하며, 매판 다른 캐릭터 조합이 나와야 한다.

## 마무리

**이 프로젝트가 증명하는 것**:
- 1인 개발자가 **AI 에이전트 오케스트레이션**으로 설계·구현·검증을 전문 역할로 분업하며 개발 속도와 품질을 동시에 확보하는 워크플로우
- "실행됐다"에 안주하지 않고 **독립 검증·회귀 테스트·근본원인 추적**을 규율로 지키는 개발 문화
